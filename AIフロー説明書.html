1全体像 — AIは2つある

このアプリが使うAIは Codex（ChatGPTの枠） と Gemini の2つだけ。 どちらを使うかは機能ごとに固定されているのではなく、設定されているものを上から順に試す形になっている。

flowchart TD
  T["先生が「つくる」を押す"] --> K{"Codex の合言葉が
入っている？"}
  K -- はい --> C["Codex
gpt-image-2"]
  K -- いいえ --> G["Gemini
APIキー（BYOK）"]
  C -- "つながらない" --> G
  C -- できた --> S["Storage へ保存"]
  G -- できた --> S
  G -- "キーも無い" --> E["理由を出して止まる"]
  S --> V["機械検査を通す"]
  V --> D["下書きに入る"]
ここだけ覚えれば足りる：
① 絵は Codex が第一、届かなければ Gemini。
② 文章と音声は いまのところ Gemini だけ。
③ どちらも「先生自身のアカウント」で動く（アプリは共有の鍵を持たない）。

2なぜ Codex が第一なのか

2つの理由がある。どちらも実測にもとづく。

  1. 絵の水準が高い。 Codex の組み込み image_gen（既定モデル gpt-image-2）で、 設定画を参照させながら12枚を作り直しゼロで生成できた（ネクマックス6体・登場人物2人・まんが4コマ）。
  2. Gemini の無料枠が少ない。 教材づくりは1本あたり十数回の生成になるので、 枠の消費が運用の制約になる。Codex は ChatGPT のサブスク枠で動く。
Codex は ChatGPT ログインだけで動く（2026-08-06 実測・codex-cli 0.145.0）。 OpenAI の APIキーは要らない。codex login 済みであればよい。

Gemini を残してある理由

Codex は先生のPCで常駐プロセスを動かしている間しか使えない。 ブリッジを止めているとき・別の端末から触るときのために、Gemini の経路を残してある。 絵づくりでは、Codex に届かなければ黙って Gemini に回る—— 先生が絵を待っている場面で、ブリッジが止まっているというだけで手が止まるのは割に合わない。

3つながり方（公開URL → 手元のCodex）

公開中のアプリ（https://…workers.dev）から、先生のPCで動く Codex を使える。 Cloudflare Tunnel もドメインも Access も要らない。

sequenceDiagram
  participant B as ブラウザ
(公開URL・https)
  participant R as codex_bridge
(先生のPC :8790)
  participant X as codex app-server
(:17653)
  B->>R: GET /api/codex/hello?token=…
  R-->>B: { workdir }
  B->>R: PUT /api/codex/file?token=…&name=ref_x.webp
  Note over B,R: 設定画を作業フォルダへ置く
  R-->>B: { path }
  B->>R: WS /codex?token=…
  R->>X: ハンドシェイクを肩代わり
  B->>X: turn/start（localImage + 指示）
  X-->>B: imageGeneration completed
  B->>R: GET /api/codex/file?token=…&name=out_y.png
  R-->>B: PNG（1536×1024）

なぜ https のページから ws://127.0.0.1 が開けるのか

127.0.0.1 はブラウザの規格上「安全なオリジン（potentially trustworthy）」に数えられるため、 混在コンテンツの遮断にかからない。2026-08-06 に公開URLのページから接続して OPEN を確認した。

だから合言葉が必須になった。 つながるということは、先生が開いたどのサイトからもこのブリッジを叩けるということでもある。 その先にいる Codex はパソコンの中でコマンドを実行できる。
  • ブリッジは起動時に合言葉を作って表示する（~/.nexmax/codex-bridge-token・本人だけ読める権限）
  • WSもHTTPも、合言葉が合わなければ 401。上流には1バイトも通さない（時間の一定な比較）
  • ファイルの受け渡しは作業フォルダ1つの中だけ。名前も [a-z0-9_-]{1,64}.(png|jpg|jpeg|webp) に限る
許可リストではなく合言葉を境界にしたのは、非ブラウザからはオリジンを自由に名乗れるため。

先生の手順

cd <リポジトリ> && npm run codex:bridge
# 画面に出る合言葉を /admin/ai の「合言葉」に貼って「接続」

5絵をつくる

入口は1つ（src/components/studio/image-api.ts の generateImage()）。 エリアの絵・設定画・まんがのコマが、みんなここを通る。呼ぶ場所ごとに書くと、失敗の言い方が画面ごとにばらけるため。

flowchart TD
  A["generateImage(prompt, references)"] --> B{"合言葉あり？"}
  B -- はい --> C["generateWithCodex"]
  C --> C1["参照画像を PUT"]
  C1 --> C2["WS で turn/start"]
  C2 --> C3["GET で受け取る"]
  C3 --> OK["File を返す"]
  B -- いいえ --> G
  C -. "つながらない" .-> G["POST /api/studio/image"]
  G --> G1["サーバが参照画像を取りに行く
（最大4枚）"]
  G1 --> G2["Gemini generateContent"]
  G2 --> OK

一貫性の作り方（これが要）

  • 設定画（model sheet）を先に1枚作り、コマ絵の生成で毎回参照入力に渡す。 プロンプトで毎回容姿を書き直すより確実。
  • さらに1コマ前の絵も参照に足すと、部屋・光・服がそろう。 実測では4コマとも1回ずつの生成で、服・髪・部屋が一致した。
  • 参照画像は最大4枚（Worker の外部subrequest上限が50本のため少なく抑える）。
絵に日本語を描かせない。 ふりがな入りの画像生成は成功例が1件も見つからなかった。拡散モデルは文字を言語ではなく ピクセル模様として学習するため、ルビは (a) 本文より小さい (b) 位置が厳密 (c) 画数の多い漢字の真上 という三重苦になる。 吹き出しは空で描かせ、セリフはアプリが重ねる。

6文章をつくる

いまの経路（Gemini・サーバ側）

まんがの台本と ことばの抜き出しの2つ。どちらもサーバの Route Handler が generationConfig.responseSchema で JSON の形を機械的に縛っている。

機能入力出力
まんがの台本登場人物＋やりたいこと1行コマ割り・セリフ・読み辞書
ことばの抜き出しステージの本文語・読み・意味・英語

Codex へ寄せる土台（実装ずみ・未配線）

Gemini の無料枠が少ないため、文章生成も Codex へ寄せる方針。 codex app-server のプロトコルを出して確かめたところ、必要なものは揃っていた。

TurnStartParams.outputSchema が実在する
"Optional JSON Schema used to constrain the final assistant message for this turn."
つまり JSON の形をプロトコル層で縛れる。Gemini の responseSchema に相当するものが Codex に無い、という前提は誤りだった。TurnInterruptParams（= {threadId, turnId}）も実在するので、 長い生成に「とめる」を付けられる。

それでも受け取る側は頑丈にしてある（src/lib/ai/json-reply.ts）。縛っても前置きが混ざる余地は残るため：

  • コードフェンス ```json を外す
  • 前置き（「はい、作りました:」）と後書きを飛ばす
  • 文字列の中の括弧に釣られない（クォートの中かを見ながら走査する）
  • 途中で切れている返事は通さない — 半端な教材が「作れた」ことにされると、先生が気づかないまま公開してしまう
  • 形が違えば同じスレッドで言い直させる（新しいスレッドだと同じ崩れ方を繰り返す）。2回で諦める

7音声をつくる

Gemini Live の TTS。Codex に対応するものが無いので、ここは Gemini のまま。

sequenceDiagram
  participant B as ブラウザ
  participant S as /api/live/token
  participant L as Gemini Live
  B->>S: POST（先生のキー）
  S->>L: 短命トークンを発行
  S-->>B: token だけ返す
  Note over B,S: キーはクライアントへ返さない
  B->>L: WebSocket（token）
  loop 台本の1行ずつ
    B->>L: テキスト
    L-->>B: PCM
  end
  B->>B: つないで1本の WAV に

声は登場人物DB（character.voice）から名前で引く。 リスニングの participants は声を持たない——同じ人が別の教材に出ても声が変わらないようにするには、 人物のほうに1つ持たせるしかないため。

8学習者が使うAI（たいわ）

唯一、学習者が直接AIと話す機能。Gemini Live の双方向音声。

  • サーバは短命トークンを発行するだけ。長時間の WebSocket を Worker で中継しない （Cloudflare Workers の制約を避ける設計）
  • キーは先生が登録したもの（BYOK）
  • 失敗の理由を区別して出す（tokenRejected / noPermission / modelNotFound / rateLimited / upstream）
モデル名は入れ替わりが速い。src/lib/ai/models.ts に1か所だけ書き、 上から順に試す。2026-08-06 の不具合は、コードが指していた preview モデルが消えていたのが原因だった。

9まとめて つくる

/admin/batch。全教材を1回走査して、まだ絵や音の無いところを1つの並びにする。

flowchart LR
  A["全教材を走査"] --> B["足りないものの一覧"]
  B --> C{"上から1件"}
  C --> D["つくる（絵 or 音）"]
  D --> E["Storage へ置く"]
  E --> F["教材へ入れて保存"]
  F --> C
  C -- "とめる が押された" --> G["ここまでは保存ずみ"]
直列にしてある理由：ブリッジは1接続1操作なので、並列にすると2件目から 「前の生成が終わるまで待ってください」で落ちる。直列は遅いが、 失敗した1件だけをやり直せる。
1件できるたびに保存する理由：絵は1枚に1分前後かかる。8枚なら8分。 まとめて最後に保存すると、とめたぶんもブラウザを閉じたぶんも全部消える。

「無い」の判定は src で見る

status は見ない。"generating" はタブを閉じても更新されないので、 「作っている最中のまま永久に残った嘘」を掴んでしまう。実体があるかどうかだけが信用できる。

10生成物が通る関門

AIが作ったものも、人が書いたものと同じ検査を通る。 「誰が作ったか」でなく「検査を通ったか」で公開可否を決める。

検査何を見るか下書き公開
禁止語「不正解」「間違いです」「ダメ」errorerror
ふりがなの覆い学習者が読む文の漢字が読み辞書で全部覆えているかwarnerror
秘匿の漏れ質問で引き出す事実が調査ページに書かれていないかerrorerror
国名「タイ」は error／ほかの国名は warn（確認の合図）error / warnerror / warn
スキーマsrc/content/schema.ts（zod）errorerror
2026-08-07 に3つの穴を塞いだ。 どれも既存の穴で、AIの生成量が増える前に締めたもの。
  • 保存経路にふりがな検査が無かった — スタジオ製の教材はCIを通らないまま公開できていた
  • 秘匿漏れが warn 止まりで、終了コードにも保存の可否にも効いていなかった
  • 国名の規律に検査コードが1行も無かった — 人が読んで気づく前提の規律は、AIが作り始めた瞬間に破れる
