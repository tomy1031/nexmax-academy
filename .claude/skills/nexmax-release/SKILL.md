手順の正は `docs/deploy.md` §0（特に **§0.6 リリースの輪**）と AGENTS.md「統合とデプロイ」、
そして `docs/constraints.md`。**作業前に3つとも Read すること。**

> **いちばん間違えやすいところ**: 本番は **「本番OK」を待たない**。
> 2026-08-21「これチェックする時間がないため、対応終わったら速攻でデプロイしてください」で
> 待つのをやめた（`docs/constraints.md` 製品の制約）。待っていたころは STG が1日14回
> 更新されたのに本番は2回で、直したものが何日も学習者に届かなかった。
> **ユーザーに「本番OK と返してください」と求めるのは、この決まりに反する。**

骨子（詳細は上記の文書）:

1. **作業中の確認** → `npm run cf:branch`（自分専用URL。stagingに上げない）
2. **出す前の検収（教材・会話UIを変えたとき）** → 作った本人ではない目（別セッション/
   エージェント）が、設計01 §4 失敗カタログ＋意地悪条件（文の途中で5秒止まる・声をつながない・
   言い直す・回線が切れる）で通しプレイしてから統合する（2026-08-19 導入・願い #97）
3. **統合** → 先に `origin/main` を取り込む → AI が PR 作成 → CI green で AI がマージ →
   **STG は main への push で自動反映**（Actions「デプロイ」。鍵は GitHub 側。
   手元で `cf:staging` を叩かない）。STG の `/api/version` が main の SHA になったことを確認
4. **本番（続けてすぐ）** → 機械の検査（vitest・e2e・lint・CI）が通っていれば、
   **確認を待たずにその場で出す**。`gh` が無いセッションでは GitHub MCP の
   `actions_run_trigger`（`run_workflow` / `deploy.yml` / ref=main / inputs `{target: production}`）。

   ```bash
   gh workflow run deploy.yml -f target=production   # gh があるとき
   ```

   ワークフロー自身が `/api/version` を突き合わせて、載っていなければ落ちる。
   完走を見届け、本番 `/api/version` が main の SHA と一致したことを自分でも確かめる。
5. **報告** → 「URL＋操作＋見るポイント」は これまでどおり添える。ただし
   **OKを求めない**（見るのはユーザーの都合のよいときでよい）。
   本番へ出したので「本番待ち」のタスクは作らない・残さない
6. 反映後は**主要ページの生存確認**をし、変えていない画面が変わっていないことも確認
   （= 引き算検証）

## 見るURLを取りちがえない

ユーザーが「変わってない」と言ったら、**まずどのURLを見たかを確かめる**
（2026-08-22 に実際に起きた。本番だけ古いまま置いていた）。

| | URL | 更新のされかた |
| --- | --- | --- |
| 本番 | `academy.nexmax.workers.dev` | **手動**（上の手順4）。ここが遅れると学習者に届かない |
| STG | `staging-academy.nexmax.workers.dev` | main への push で自動 |
| ブランチ | `<ブランチ名>-academy.nexmax.workers.dev` | `npm run cf:branch` |

どこが何を載せているかは `/api/version` の `sha` で分かる（ビルド時のコミット）。
**ログインなしで中身まで見たいときは `/api/<でたらめな名前>`** を開く
（middleware は `/api/` を通すので、404画面がそのまま見える）。
