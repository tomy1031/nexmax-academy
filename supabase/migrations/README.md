# 移行SQL — なぜ「同じ名前」のファイルが2つあるのか

`personality_results` や `quiz_results` のように、**同じ名前で版だけ違う**ファイルが
並んでいる。写し間違いではない。**どちらも本番DBに実際に流れている。**

## 起きたこと（2026-09-04 に台帳を突き合わせて分かった）

このリポジトリでは、鍵（`SUPABASE_DB_URL`）が無かった時期に **2つの経路**で
移行SQLを流していた。

| 経路                      | 版のつけかた                                            | `statements` |
| ------------------------- | ------------------------------------------------------- | ------------ |
| Supabase CLI（`db push`） | CLI が **流した時刻**でつける（例 `20260819042046`）    | SQL が入る   |
| コネクタで手で流す        | **ファイル名の版**を手で記録する（例 `20260817120000`） | 空           |

先に CLI で流し、そのあとファイルを直してコネクタで流し直す、ということが
何度かあった。結果、DBの台帳には **30版**あるのに、リポジトリには **14本**しか
無い、という状態になっていた。

`supabase db push` は「リモートにあってローカルに無い版」を見つけると

```
Remote migration versions not found in local migrations directory.
```

で止まる。**鍵を入れた日に、これが2つめの壁として待っていた。**

## どう直したか

CLI が流した16本を、DBの `supabase_migrations.schema_migrations.statements` から
**そのまま取り出してファイルに戻した**（md5 でバイト一致を確認ずみ）。
消す（`migration repair --status reverted`）道もあったが、そちらは

- 本番の台帳を書き換える（授業のある日にやりたくない）
- **11本はリポジトリのファイルと中身が違った**＝先行版の記録が消える

ので採らなかった。いまのリポジトリは **DBが実際に受け取った順番そのもの**である。

## これから

- 移行SQLは `integration` に入れれば「デプロイ（DB）」ワークフローが流す
- 流れたかどうかは `node scripts/check_migrations.mjs` が見張る
- RLS が効いているかは `node scripts/check_rls.mjs` が見張る
- **手でコネクタから流さない。** 2つの経路が並ぶと、また台帳が割れる
