## 2. この教材で作るもの（前のセッションで合意ずみ。ここは変えない）

朝礼・夕礼は、**いま報告ステージ（`/houkoku`）の後半6本**に入っています。これを**別ステージへ切り出します**。

**学習の形**（ここが芯）:

```
場面が 渡される → 見本（だれかが 先に 報告する）→ あなたが 1本 報告する
→ 言えた 要素の パネルが 開く（複数 同時に 開く）
→ 足りない パネルだけ 司会が 聞き返す → 全部 開いたら
→ ほかの メンバーが 報告 → 上の 人が まとめて 終わり
```

いまの朝礼ミーティングは「**アプリが5問を順に聞き、学習者が1問ずつ答える**」形です。これをやめます。

**ユーザーの原文（前のセッション）**:
- 「ここの報告では、正しい要素を正しく伝えられることが目的なので、**正確に伝えられているかを判定して、伝えられていない場合は、追加で足りていない情報に対する質問を繰り返してくれるとありがたい**」
- 「**一度に複数答えられている場合は複数のパネルが開く**といいですね」
- 「最初は答える人の見本が見られるといいので、**別な人が報告を先に行った上でそれと同じように報告させたい**」
- 「全部開いたら、残りのメンバーの報告を行った上で、**藤木取締役が、お客様の反応が現在どういう状況か、全体がどのように努力していくべきかを統括して**、ミーティングを終わりとしたい」
- 「**ミーティングは朝礼なので、複数名で参加して欲しい**です。にゃむさんや奥田さん、藤木さんなど」
- 「**💗 ヘンディさんとの きょり 0/5 というパラメーターは意味不明です。**正しく自分の状況を伝えられるのが重要なことなので、**距離もエピソードも無駄しかありません**」
- 「時間が経過したことがわかるアナウンス（モーダルなど）を入れることで、**一つのもので成り立つようにしたい**」

## 4. エンジンの調査結果（前のセッションで確認ずみ。読み直す手間を省くため）

**足りない部品は4つだけで、土台はほぼ揃っています。**

| 要ること | いまの状態 |
| --- | --- |
| **1発話で複数パネルを開く** | `src/components/listening/req-matcher.ts` に **3層判定（AI＋キーワード＋手動）が実装ずみ。鍵ゼロでも層2だけで動く**。**ただし `parseReqJudge` が返すのは id 1つ**。ここを「複数」にする（純関数なので単体テストで守れる） |
| **複数名の参加** | `meetingSchema` の `host` は**1人だけ**。`participants[]` を足す（listening は既に持っている形） |
| **場面（ラウンド）と時間カード** | ミーティングは1本＝1場面。`src/components/talk-game/talk-game-session.tsx` は「ばん」を持ち、板もばんの数だけある（参考になる）。**かんたん・むずかしいの両方に要ります**（§1-5） |
| **スキップ可にする** | ステージの `contents[]` の項目に `gates: false` を書けば関門から外せます（種別の既定を上書きできる。実例: `content/stages/intro.json` の `it_orientation_check`）。**むずかしいほうにこれを使います** |
| **日本語の見かたを深くする** | `src/components/meeting/japanese-check.ts` に**ルールで見る層**があり、いま4つだけ（empty / tooShort / notPolite / noPeriod）。**このファイル自身が「意味の当否や自然さはAIを足すときに外側へ重ねる」と書いており、広げる前提で作られています** |

## 5. やさしい／むずかしい の切り替え（ユーザーの案。4つとも実装可能と確認ずみ）

**ユーザーの原文**:
> やさしい / むずかしい に分けて、ヒント（穴埋めの例文）の表示非表示をデフォルトで分ける、
> もしくはヒントがより答えを導けるものか、考えさせるものか で分けるようにするなどは可能ですか？
> プロンプトが返す言葉の難易度も分けられるとなおいいですね。N3レベル、N4/N5レベルで切り替えるようにすればできるかもしれない。
> 評価する内容についても、「N3レベル」としてふさわしいか、のような文面の「」を切り替え可能にすればうまくいくかな。

| 案 | 実装場所（確認ずみ） |
| --- | --- |
| ①ヒントの表示/非表示の既定を分ける | `freeSchema` は `starter`（打ちながら見える型文）と `hints[]`（ボタンの向こう）を**別々に持っている**ので、既定の開閉を切り替えるだけ |
| ②ヒントを「導く型」と「考えさせる型」で分ける | `hints[]` は配列なので**2種類持てる**。**前のセッションではこれが本命と判断** |
| ③AIが返す言葉の難易度を切り替え | 相手の話し方は `src/lib/meeting/instructions.ts` の `commonRules(source.persona)` が組み立てている。**レベルの1行を差し込むだけ** |
| ④評価の文面の「N3レベルとして」を切り替え | `src/components/meeting/judge-api.ts` の `JUDGE_SYSTEM` に **「日本語N5〜N4」とべた書きされています**。ここを差し替え可能にする。**「ふさわしい」の中身を段ごとに列挙しないとAIの判定が揺れます** |

**※ 教材を2つに分けるので（§1-5）、①②は「教材ごとに違うデータを持つ」だけで実現します**（画面の切り替えの仕組みは要りません）。
③④は**教材ごとにレベルの文字列を持つ**形になります。

**注意**: 前のセッションで「**難しさを日本語で作らない**」と書いたら、ユーザーに否定されました。
> 「これは記載しない。**日本語の難易度で分けることも時に必要**」

## 6. やってはいけないこと（前のセッションの失敗。全部ユーザーに指摘されたもの）

1. **既存の顧客・案件・キャラを、順番を確かめずに流用しない。**
   前のセッションは Aoba抹茶カフェ・そら書店を使って却下されました。理由は「**先のステージで紹介する内容なので、的外れ。むしろ後工程の害になる**」。
   → **使ってよいのは、そのステージより前に出ているものだけ。** 無ければ完全オリジナルを作る（規律10・R9-9）。
2. **曜日と難易度を同じ軸に重ねない。**「レベルごとに曜日の朝礼を分けたら、混乱をまねくのはわかりませんか？」
   → **内容が変わるなら、変わったことが画面で明確に分かるようにする。**
3. **背景知識の説明が要る題材にしない**（今回の保育園の却下理由）。
4. **裏設定なしでセリフを書かない。**「どのような案件で現在どのような状況まで進んでいて、それぞれどのような進捗なのかは**裏設定として考えた上で**、それぞれのメンバーのセリフを考えるべき」
   → ただし**その裏設定が複雑になりすぎると今回のように却下されます**。**やさしさと両立させてください。**
5. **曖昧な描写をしない。**「エラーの意味が分からない（30分止まっている）」→「**具体的なエラーを**」と指摘されました。
6. **名前のある登場人物にミス役をやらせない。** 松井社長を除く全員が**実在の社員・役員がモデル**。
   ミス役が要るなら**仮のキャラクターを作る**（山田さん・鈴木さんなど）。ただし**そのキャラの説明コストが見合うか精査すること**。
7. **主人公から見て、名前のある登場人物はみんな先輩。**「同期」「同僚」にしない。
8. **設問はヒントを閉じたまま答えられること。** ヒントは足場であって前提ではない（R10）。
9. **実在の制度・自治体の具体的な条件（金額・補助率）を書かない。** 自治体ごとに違うので、事実として書くと誤りになります。
10. **おせっかいの一言を足さない。** ユーザーの原文:「**いつも私が意図を持ってやっていることを勝手に破壊されたり、余計な一言を加えられます**」。
    移植・改稿では `node scripts/diff_port.mjs <旧URL> -- <新JSON>` で**足した文・削った文を並べて確認**してください。

## 7. 進め方

`docs/constraints.md`「**AI生成は必ず段階を踏む**（作りたいもの→AIが案→人が修正・承認→次の段階）。一発生成にしない」に従ってください。

1. **khmersabai.com を調べる**（何のサービスか、誰向けか）
2. **題材と裏設定の案**を出して**承認をもらう**（ここで止まる。実装に進まない）
3. 承認後、シナリオ本文 → エンジン → データ → ステージ分離 の順に、**各段でSTGに出して見せる**

**検収**: 教材を触るターンは、`rubric-checker`（担当 R1〜R11。**並べ替え・新設なら R9 は必須**）と、
**N5・N3 のペルソナ通し**を必ず回してください。**ペルソナはデータを読むだけでは「遊べるか」を測れません**
（前のセッションで、読むだけのペルソナが報告クエストを「一番おもしろい」と評価しましたが、
ユーザーが実際に遊んだら「何を選ぶのが正解かさっぱり分からない」ものでした）。`playwright-player` を使ってください。

**報告のしかた**: ターン末尾は10行以内。`✅結果 / 📁範囲 / 🧪証拠（URL→操作→期待）/ ⏭次の一手（1つ）/ ❓判断（0〜1個・A/B択）`。
**ユーザーは動作確認をしません。**通しの確認は機械（`npm run e2e`）でやります。
