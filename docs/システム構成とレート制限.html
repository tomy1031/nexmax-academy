天井マップ — 構成と、無料枠のどこに当たるか

このアプリは Cloudflare・Supabase・Google の無料枠だけで動いている。 無料枠は「速度が落ちる」のではなく ある数を超えた瞬間に止まる。 どこに天井があり、どの作業がそれを削るのかを1枚にまとめる。

2026-08-27 現在 出典: リポジトリ実コード ・ docs/deploy.md §0.4〜§0.10 の実測

1全体像 — 天井を持っている大家は4人

サーバは1つではない。学習者のブラウザは 3つの相手と別々に話す—— うちの Worker、Supabase、そして Google（学習者自身のキーで）。 天井もその相手ごとに別々に立っている。

この形になっている理由は2つ。

  • Worker に仕事をさせない。 無料枠の CPU は1リクエスト 10ms。 Cloudflare 自身が「サーバ側描画や認証は 10〜20ms 使う」と書いている—— 構造的にはみ出すので、描画も認証も外に出した。
  • キーを預からない。 Gemini のキーは学習者・先生が自分で発行し、その端末にだけ置く（BYOK）。 アプリは共有キーを持たないので、Google の枠は使う人ごとに別勘定になる。

2天井の一覧 — どこに、いくつ、超えると何が起きるか

「レート制限」と呼んでいるものは、実際には性質の違う3種類が混ざっている。 1日で戻るもの・一度に何回かで決まるもの・戻らない容量。 混ぜて考えると対策を間違える。

A. 1日で戻る枠（日付が変わるとリセット）

天井数超えると削るのは
Worker リクエスト 100,000 / 日 Error 1027。UTC 0時（カンボジア朝7時）まで全員止まる HTML・API・RSC のアクセス全部（静的アセットは数えない）
KV 読み（作りおきを読む） 100,000 / 日 作りおきが読めずフルSSRへ落ちる 作りおきページの表示。拠点キャッシュが大半を吸う
KV 書き（作りおきを置く） 1,000 / 日 code: 10048。デプロイの作りおき投入が途中で落ち、その版は全アクセスがフルSSRになる 本番デプロイ（1回 約75件）＋ ISR の作り直し

B. 一度に何回かで決まる枠（時間で戻る・IPごと）

天井数超えると削るのは
Worker CPU 10ms / 1リクエスト Error 1102。その人だけ画面が出ない（全員ではない） 冷えた Worker での dynamic ページ描画
Supabase 認証 /auth/v1/token 1時間 1,800回
ただし一度に 30回		 ログインが弾かれる。Cloudflare をいくら直しても効かない 授業開始時の一斉ログイン。教室はIPが1つなので人数がそのまま乗る
Supabase 認証 /auth/v1/verify 1時間 360回
一度に 30回		 同上 メール確認などの経路
Supabase データ /rest/v1/* 上限なし — だから進捗も名簿もブラウザから直に読み書きしてよい（RLS が守る）
Gemini Live（音声） キーごと（Google 側・こちらからは見えない） 接続が張れない → 画面は理由を出して止まる たいわ・ミーティングの判定・リスニングの音声づくり
Gemini generateContent（文字） キーごと・Live とは別勘定 すぐ上限に当たる（実測: 学習者1人の1回のミーティングで尽きた） 先生の教材づくりだけ。学習者の画面では使わない（§5）
Codex（ChatGPT の枠） サブスクの枠 ＋ 1接続1操作 2件目以降が「前の生成が終わるまで待って」で落ちる 絵・台本の生成。だからまとめて作るは1件ずつ直列

C. 戻らない天井（容量・大きさ）

天井数いまの実測備考
KV の保存量1 GB7日で期限切れ → 約 530 MB で頭打ち 2026-08-26 に 1.24 GB で超過寸前だった。期限なしで置いていたため
Worker のコードの大きさgzip 3 MiB1,822 KiB（2026-08-16） 超えると code: 10027 でデプロイが止まる。2.8 MiB で警告する見張りが CI にいる
静的アセットの数20,000 ファイル / 版余裕 配信回数は無制限・カウント外
Supabase DB500 MB12 MB教材を全部DBに置いても問題にならない
Supabase ファイル1 GB11 MB画像・音声の置き場
要点 無料枠での基本方針は 「Worker を通る回数を減らして、静的アセットに逃がす」。 静的アセットはどれだけ配っても枠を使わない。

31回のアクセスが通る道と、そこで減るもの

画面を1つ開いたとき、どの枠がいくつ減るか。分かれ道は3つ—— 静的アセットか／作りおきがあるか／300秒を過ぎたか。

いちばん見えにくい連鎖がここ。 KV の書き込み枠が尽きる → デプロイが作りおきを置けない → その版は全アクセスがフルSSR → 授業の人数で必ず Error 1102。 つまり デプロイ回数が、巡り巡って同時アクセス障害の原因になる。 「デプロイはタダ」と思って1日に何度も出すと、その日の夕方には出せば出すほど壊れる状態になる。

4授業の始まりに何が起きるか

授業（火・水・金）の 入室の瞬間が、このアプリでいちばん負荷の高い数十秒。 2026-08-25 に単語ゲームを20人で開いて上限超過が実発生した場所でもある。

授業のある日、それぞれの天井はどれだけ埋まるか

縦の赤い線が天井。右の斜線は越えてはいけない帯で、そこまで届いた棒は超過している。

Cloudflare 自身の目安が「サーバ側描画や認証は 10〜20ms」。天井は 10ms なので構造的にはみ出す。 冷えた Worker での実測は応答 1.16〜2.09秒（温まっていれば 0.20〜0.35秒）。 20人が一斉に入ると拠点は新しい Worker を何本も起こすので、何人かが必ず「1回目」を引く—— 「全員落ちる」ではなく「何人かだけ入れない」に見えるのはこれが理由。

5AI は誰の枠で動くか

アプリは共有の AI キーを持たない。使う人のキー・使う人の枠で動く（BYOK）。 だから Cloudflare の天井とは完全に別勘定で、Worker も通らない。

学習者の画面で gemini-2.5-flash の generateContent を使わない（絶対）。 Live の枠と generateContent の枠は別勘定で、後者は 学習者1人の1回のミーティングで使い切る（2026-08-20 の実測と指定）。 文字だけの判断が要るときは、Live のつなぎの中で JSON をもらうか、端末の規則ベースで済ませる。

Codex を第一にしている理由も枠の話。 絵の水準が高いことに加えて、Gemini の無料枠が少ない。教材1本の制作は十数回の生成になるので、 そこを ChatGPT のサブスク枠（先生のPCで動くブリッジ）に逃がしている。 ブリッジが止まっていれば黙って Gemini に回る。

6作業別 — どの作業が、どの枠を使うか

アプリで起きる作業を全部並べて、それぞれが削る枠を書いた。 学習者の作業のほとんどは Worker を1回しか使わないのが今の形。

作業だれ通る道削る枠
ログインする 学習者先生 ブラウザ → Supabase 認証 → /auth/callback Supabase 認証（一度に30回）／Worker 1回＋CPU（戻り道は dynamic・1人1回）
タイトル画面を開く 学習者 作りおき（force-static）＋ ブラウザで判定 Worker 1回。CPU はほぼゼロ（Next を起こさない）
まなびマップ・教材ページ・じしょ 学習者 作りおき（ISR 300秒・16ルート） Worker 1回／KV 読み 1回（拠点キャッシュが吸う）／300秒に1度だけ KV 書き
ことばアーケードで遊ぶ 学習者 入室の1回だけ。プレイ中は端末の中 入室の Worker 1回のみ。遊んでいる間はゼロ
もんだいを解く・進捗を保存する 学習者 ブラウザ → Supabase /rest/v1（RLS） 上限なし／DB 容量（500 MB のうち 12 MB）
たいわ（音声で話す） 学習者 ブラウザ → Gemini Live（短命トークン・1回きり・30分） 学習者のキーの Live 枠。Worker も Supabase も通らない
ミーティングの判定・助言 学習者 判定専用の Live 接続（音声で答えさせ、文字起こしから JSON を読む） 同上。generateContent は使わない（すぐ上限に当たるため）
教材を書く・直す（/admin） 先生 dynamic なページ（Next 本体が起きる） Worker CPU。先生は数人なので許容している唯一の場所
教材を保存する 先生 /api/studio/content → Supabase Worker 1回／DB 容量
絵をつくる（エリア・キャラ・まんが） 先生 Codex ブリッジ（第一）→ 届かなければ Gemini 画像 ChatGPT の枠／Gemini 画像の枠。1件ずつ直列（ブリッジは1接続1操作）
リスニングの音声をつくる 先生 ブラウザ → Gemini Live TTS（行ごとに1接続・声を切り替えられないため） 先生のキーの Live 枠。行数ぶん積み上がる
台本・ことばの抜き出し 先生 Codex または Gemini generateContent ChatGPT の枠／Gemini の文字枠（先生の画面でだけ許される）
STG を更新する（integration へマージ） 自動 GitHub Actions → wrangler KV 書き 0件（作りおきを温めない設計）。何回出してもよい
本番を更新する（火・水・金 17:05 ICT） 自動 GitHub Actions → wrangler ＋ 作りおき投入 KV 書き 約75件。ここが1日枠のいちばん大きな固定費
ブランチ確認URLを更新する AI npm run cf:branch（作りおきを静的アセットに写す） KV 書き 0件。開発中に何度出しても授業に響かない
通しの自動検証（e2e） 自動AI 鍵ゼロのデモモードで自分の中に立てたアプリを操作 本番の枠を使わない
同時アクセスの確認（loadcheck） AI 本番へ 20並列 × 5ページ Worker リクエスト 100回。回数を増やして連打しない

7効かせている対策 — どの決まりが、どの天井に効くか

いまアプリに入っている「一見わけの分からない決まりごと」は、ほぼ全部この表のどれかである。 外すと、対になっている天井が戻ってくる。

決まり／仕掛け効く天井外すと起きること
学習者画面の Link は prefetch={false}（53か所）Worker リクエスト マップを開くだけで1人数十リクエスト。20人で数十倍に膨らむ
images.unoptimized: trueWorker リクエスト /_next/image が素通しなのに Worker を1回消費する（変換は有料機能のため何もしない）
学習者が通る画面を dynamic にしないWorker CPU 10ms リクエストのたび Next 本体を読み込み、冷えた Worker で Error 1102
getUser() ではなく getClaims()（署名をその場で検証）Supabase 認証・Worker CPU 1画面あたり2往復 × 20人 = 40往復が同じ IP から飛ぶ
ISR の revalidate は 300秒より短くしないKV 書き 1,000/日 作り直しが5倍に増え、デプロイと枠を取り合う

学習者の画面で generateContent を使わないGemini の文字枠 学習者1人が1回ミーティングをしただけで、その日そのキーは使えなくなる

8次に折れるのはどこか

直近の危険を、近い順に3つ。

  1. Supabase の一斉ログイン（一度に30回）。 いちばん近い。20人ならまだ余裕があるが、30人クラスで確実に当たる。 Cloudflare 側をどう直しても効かず、対策は「認証の往復そのものを減らす」しかない （getClaims() はすでに入れた）。
  2. 逃がしきれない dynamic の CPU。 学習者の道からは消したが、ログインの戻り道（1人1回・必ず通る）と /map/settings・/admin/* は仕組み上 dynamic のまま残る。
  3. 授業のある日の KV 書き込み。 いまは半分ほどで収まっているが、ページ数が増えると作り直しの件数もそのまま増える。 教材が倍になれば、この枠が先に見えてくる。

まとめて外れる道がひとつだけある。 Workers 有料プラン（$5/月）に上げると CPU が 10ms → 30秒になり、 リクエストの1日上限も無くなる。§7 の Cloudflare 側の決まりはほぼ全部が不要になる。 Supabase の認証だけは別の天井なので残る。 無料枠を守る前提はユーザーの指定なので、有料化は判断待ちとして置いてある。
