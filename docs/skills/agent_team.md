# エージェント編成 — 検収を「別の目」で回す体制（ツール共通の本体）

2026-09-01（願い #298）。Claude / Codex / Gemini のどのツールからも読まれる。
`.claude/skills/kenshu/` はここを指す薄いラッパー。**ここ以外に体制のルールを書かない**（二重管理禁止）。

## 0. なぜこの形か — 過去ログの分析

設計03 §5 に多エージェント検収の設計（rubric-checker ×13・playwright-player ×3 など）は
**あったが、実行体が無かった**。`.claude/agents/` は存在せず、検収は毎回その場の
プロンプト頼みで、「やる」と書いてあるのに**やらなくても止まらない**状態だった。
その隙間で起きたのが、この体制が防ぐべき事故の一覧である:

| 実際に起きたこと                                                                             | 足りなかった目                     | 防ぐ役（今回置いた）                   |
| -------------------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------- |
| 「考え→かんが」等の誤読が CI 緑のまま 4ファイルで生存（2026-08-30）                          | 読みの正しさを見る機械と目         | `lint:content` 読みの照合 ＋ yomi-kensa |
| ヒント消滅の穴（PR #92）— ガイドに書いてあるのに実装が踏んだ                                 | 作った本人でない通しプレイ         | playwright-player（意地悪条件）        |
| 単語ゲームで誤答が正解になる・時間切れが無言（2026-08-26 #218）                              | 学習者の体験を通す目               | playwright-player（理解度プローブ）    |
| 20人同時で Error 1102（2026-08-25/26）— 学習者画面の外部往復・dynamic 化                     | 無料枠の構造を知る敵対役           | code-critic（Codex の代行）            |
| DB だけが遅れて 7人が名簿から消えた（2026-08-26）                                            | 「直った」と言う前の実測           | 主スレッドの規律（AGENTS.md）＋ code-critic |
| 「不正解」等の禁止語・国名の混入                                                             | （機械化済み）                     | `lint:content`（既存）                 |
| 教材の理解設計の劣化（数の宣言・唐突な話題転換・預言的フィードバック等、01 §4 のカタログ）   | ルーブリックで審査する別の目       | rubric-checker（R1〜R8）               |

分析の結論: **「書いてあるだけのルールは守られない」**（2026-08-31 の実証:
STG 許可の一件は、ルールでなく道具の設定が止めていた）。だから体制は
(1) 機械にできる検査は `lint:content` へ入れて CI で止める、
(2) 機械にできない判断は **名前とペルソナを持つ実行体**（`.claude/agents/`）へ渡す、
の2段で「回るかどうかが道具で決まる」形にする。

## 1. 体制の全体図

```
主スレッド（作る人・進行役）─ 実装・教材執筆・統合・最終判断。最上位モデル
  │ 作ったら投げる（自分の通しプレイは検収と数えない — constraints 2026-08-19 #97）
  ├─ rubric-checker ×並列 …… 理解設計の審査（R1〜R8 から担当1セクションずつ）
  ├─ yomi-kensa      …… 読みの検収（機械照合の結果を分類・例外台帳の番人）
  ├─ playwright-player …… 実機の通しプレイ（デモモード・意地悪条件・理解度プローブ）
  ├─ code-critic     …… コード・セキュリティ・無料枠の敵対レビュー（Codex の代行）
  ├─ Codex（ローカル機のみ）…… code-critic と同じ観点の本家。§5
  └─ persona-verifier（Gemini）…… Live ペルソナの実機統計（.gemini/rules.md。変更なし）
```

- 判定は合議ではなく**指摘の和集合**。全員「違反を見つけたら勝ち」のフレーミング（設計03 §4）。
- 指摘には**必ず引用**（ファイル＋行 or フィールドパス）。引用できない指摘は出さない（AGENTS.md）。
- 感想・褒め言葉は書かない。直すのは主スレッド（検収役は手を動かさない）。

## 2. 役割表（いつ・誰を・何のために）

| 役                    | 必ず呼ぶとき                                                       | モデル | 見るもの                                                             | 出す形                               |
| --------------------- | ------------------------------------------------------------------ | ------ | -------------------------------------------------------------------- | ------------------------------------ |
| **rubric-checker**    | 教材・シナリオ・会話UI・フィードバック文言を作った/直したターン    | opus   | `docs/design/review_rubric.md` の**担当1セクションだけ**（並列に複数体） | ルーブリック指定の報告形式           |
| **yomi-kensa**        | content/ の教材データ・読み台帳（ai-kanji 等）を触ったターン       | opus   | `npm run lint:content` の読みの照合・例外台帳（yomi_allow）の妥当性  | 直す/allow の判定表＋根拠の引用      |
| **playwright-player** | 画面のフロー・学習エンジン・順路を触ったターン                     | sonnet | デモモードの実機通し（指定ペルソナ＋意地悪条件）                     | 理解度プローブの答え＋スクショの並び |
| **code-critic**       | エンジン・API Route・認証/DB・共有部品・ミドルウェアを触ったターン | opus   | セキュリティ/RLS・無料枠の罠・E2E の穴                               | 引用付きの指摘（重大度つき）         |

- 1回の実行で**1つの観点だけ**（rubric-checker は1セクション、player は1ペルソナ）。
  1体に全部見せると注意が希釈される（設計03 §4「1エージェント1原則」）。
- 検収役は**担当の必読ドキュメントを実行のたびに Read する**（ペルソナ定義に列挙してある）。
  定義ファイルへ中身を写さない——正はドキュメント側（二重管理禁止）。

## 3. モデル選定の方針（2026-08-14 の指定の運用化）

constraints.md「実装はタスクの難易度に応じて Opus / Sonnet を使い分ける。
設計判断・統合・検収は上位モデルが担う」を、そのまま既定値にする:

| 仕事                                                     | モデル                 | 理由                                                                 |
| -------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------- |
| 設計判断・統合・教材の執筆・最終判断（主スレッド）       | 最上位（fable / opus） | 判断の質が全部の上限になる                                           |
| 検収（rubric-checker / yomi-kensa / code-critic）        | opus                   | 「検収は上位モデル」の指定。学習者向け日本語と設計の審美眼が要る     |
| 試遊の運転（playwright-player）                          | sonnet                 | 操作は機械的。**観察の解釈と最終判断は主スレッド（上位）がやる**     |
| 機械的なデータ量産・一括変換                             | sonnet                 | 「機械的なデータ・文言作業＝Sonnet」の指定                           |
| haiku                                                    | 使わない               | 学習者向け日本語の判断を任せない（読めるかどうかが最優先の製品のため） |

## 4. 回しかた（主スレッドの手順 — `/kenshu`）

1. **機械が先**: `node scripts/check_fast.mjs`（整形・型・lint:content・単体。読みの照合もここに含まれる）。
   機械で赤いうちに LLM 検収を回さない（安い順に落とす）。
2. **触った領域から役を選ぶ**（§2 の表）。教材なら rubric-checker を、**変えた教材に関係の深い
   セクションから** 2〜4体並列（全8セクションは新作のとき）。プロンプトで担当を1つ渡す:
   例「担当: R5。対象: content/articles/houkoku_lecture.json」。
3. 指摘の**和集合**を主スレッドが直す。直したら赤かった検収だけ再実行。
4. 証拠（引用・スクショ・検査ログ）を PR 本文に貼る。検収を通した印の無い教材 PR は作らない。
5. リリースは `.claude/skills/nexmax-release`（既存）へ。

## 5. Codex の使い方（批判的レビューの本家）

Codex はローカル機（ChatGPT ログイン済み）でだけ動く（docs/codex-backend.md §1。
クラウドのセッションには codex CLI が無いので **code-critic が同じ観点を代行**する）。

ローカルでの起動レシピ（読み取り専用・1観点1実行）:

```bash
codex exec --sandbox read-only "AGENTS.md と docs/design/review_rubric.md を読み、
セクション R◯ の観点だけで content/◯◯.json を審査。違反を見つけたら勝ち。
指摘には必ず該当箇所の引用を付ける。引用できない指摘は出さない。感想不要。"
```

- コード審査（認証/RLS・無料枠・E2Eの穴）も同じ形で `--sandbox read-only` のまま投げる。
- 生成（文章・画像）を Codex 第一にする方針（constraints 2026-08-07）は従来どおり
  `docs/skills/codex_image_generation.md` / `docs/codex-backend.md` 側の管轄。

## 6. やらないこと（過去に捨てた形を戻さない）

- **感想型ペルソナ検収**（旧 n4-student「どう感じましたか」）— 計測・証拠・試遊・実測に置き換え済み（設計03 §4）。
- **1体に13原則ぜんぶ**を見せる — 注意が希釈される。
- **CLAUDE.md / AGENTS.md / .gemini に別内容**を書く — 正は1か所（このファイルとルーブリック）。
- **検収役に直させる** — 直すのは主スレッド。役割が混ざると「自分の直しに自分で合格を出す」に戻る。
- **CI に LLM 検収を組み込む** — 揺れで赤くなると機械検査まで信じられなくなる（constraints 2026-09-01 の eval と同じ判断）。CI は機械検査だけ。
