# バックアップと復旧（現状と手順）

調査日 **2026-08-20**。この文書は「いま壊れたら、どこまで戻せるか」を書いた運用手順書。
数字は当日の実測（Supabase MCP でのクエリ結果）。

## 0. 結論（先に読む）

**バックアップは動いていない。復旧点（戻せる時点）は 1 つも無い。**

- Supabase の自動バックアップは **Pro / Team / Enterprise だけ**。無料プランは
  「自分で書き出して、外に置いておくこと」と公式が案内している
  （[Database Backups](https://supabase.com/docs/guides/platform/backups)）。
- このリポジトリにも書き出しの仕組みは無い。根拠:
  - `.github/workflows/` は `ci` / `deploy` / `meeting-audio` の 3 つだけで、定期実行（`schedule:`）は無い
  - `scripts/` に dump / export の類は無い
  - 端末の定期タスクにもバックアップは無い
  - `git log` に backup / dump のコミットは無い
- したがって、いま学習者データが壊れた場合、**元の値に戻す道は無い**（下の §3 参照）。

> プランの確認だけは画面でしかできない。Supabase ダッシュボード → **Database › Backups**
> を開いて「Pro 以上の日次バックアップ一覧」が出るかを見る。出なければ無料プラン＝上の結論のまま。
> 無料枠で運用する制約は `docs/constraints.md`（「インフラ・API は無料枠内。有料化は事前承認」）。

## 2. 壊れかたは 2 種類ある

| 種類                   | 例                                                       | 効く備え                     |
| ---------------------- | -------------------------------------------------------- | ---------------------------- |
| **上書き・消し込み**   | 実機検証で本人の診断結果を上書き（2026-08-04 に実発生）  | バックアップ（今は無い）     |
| **プロジェクトごと消失** | Supabase プロジェクトの削除・無料枠の停止               | バックアップ（今は無い）     |

いまは前者を「事前に SQL で現在値を退避してから触る」という**手作業のルール**だけで防いでいる
（`docs/skills/browser_e2e_verification.md`）。ルールを踏み外した瞬間に穴が開く。

## 3. いま壊れたら、どこまで戻せるか

| 対象                       | 戻せるか       | 戻しかた                                                          |
| -------------------------- | -------------- | ----------------------------------------------------------------- |
| 表の作り（スキーマ・RLS）  | **ほぼ戻せる** | `supabase/migrations/*.sql` を順に適用（§4 の穴を手で埋める）      |
| 教材の中身                 | **種まで戻せる** | git の `content/**/*.json` 40 件。**スタジオでの直しは失われる**  |
| 学習者の記録（診断・解答・発話・なまえ） | **戻せない** | 出どころが DB だけ。写しがどこにも無い                 |
| ログイン（アカウント）     | 作り直しのみ   | 各自が Google で再ログイン → **別の id** が振られ、古い行と繋がらない |
| 生成物（まんが画像・音声） | 作り直しのみ   | 再生成（画像は生成コストがかかる）                                |

**教材の注意**: 同じ ID なら **DB が git に勝つ**（`src/lib/content.ts` の `mergeContentsById`）。
つまり画面に出ているのは DB の版で、スタジオで直した内容は git に戻していない限り DB にしか無い。
git→DB へ流し込む道はまだ実装されていない（願い #124 の設計段階）。

### 全損したときの順番

1. **書き込みを止める**（原因が検証スクリプトや AI セッションなら、まずそれを止める）
2. **範囲を切る** — どの表が、いつから壊れたか。`created_at` を持つ表は時刻で絞れる
   （`quiz_results` `personality_results` `meeting_turn_logs`）
3. **スキーマを作り直す** — `supabase/migrations/` を古い順に適用。§4 の欠けを手で足す
4. **教材を戻す** — git の `content/**/*.json` がそのまま効く（DB が空なら git の版が出る）
5. **学習者データ** — 復旧不能。学習者に再ログインしてもらい、診断はやり直し
6. **確認** — `npm run e2e`（通しプレイ）と主要ページの生存確認。証拠のスクショは CI が残す

所要は 1〜2 時間（データの復旧がゼロなので、実質はスキーマと教材の再構築だけ）。

## 4. 既知の穴

1. **git に無い SQL がある。** DB には 12 個のマイグレーション履歴があるが、git には 9 ファイルしかない。
   `academy_core_schema` / `academy_rls_policies` / `academy_fix_function_search_path` に当たる SQL は
   リポジトリのどこにも無い（`class_unlocks` `unit_vocabulary` などで全文検索して 0 件）。
   これらが作った 13 表のうち **`public.users`（26 行）は現役**なので、全損時は手で書き直すことになる。
2. **Storage はどのプランでもバックアップの対象外**（公式明記）。有料にしても `assets` の 21 ファイルは守られない。
3. **`auth.users` は書き出しの対象になりにくい。** Admin API で一覧は取れるが、
   同じ id のまま作り直せるかは未検証。id が変わると `profiles` などの行と繋がらない。
4. **手元に道具が無い。** この環境に `supabase` CLI も `pg_dump` も `psql` も入っていない。
   いま手で dump を取ろうとしても、まず導入から始まる。

## 5. 無料枠でできる備え（提案・未着手）

| 案                                        | 中身                                                                                                          | RPO / 手間                    | 費用    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------- |
| **A. 毎晩の自動書き出し（推奨）**         | GitHub Actions の定期実行で、service role key を使い PostgREST から全表を JSON に書き出し＋Storage をダウンロード。まとめて暗号化し、Actions のアーティファクト（90 日保存）か非公開リポジトリへ置く | 24 時間 / 自動（人手ゼロ）    | 0 円    |
| **B. 手で月 1 回**                        | `supabase` CLI を入れて `supabase db dump` を実行し、手元に保存                                                | 1 か月 / 毎回ユーザーの手作業 | 0 円    |
| **C. 有料プラン**                         | Pro（$25/月）で日次バックアップ 7 日分。PITR は別料金（+$100/月〜）                                            | 24 時間 / 自動                | 要承認  |

A を採る場合に必要なもの:

- GitHub の Environment Secrets（環境名 `Preview`）に `SUPABASE_SERVICE_ROLE_KEY` と `NEXT_PUBLIC_SUPABASE_URL` を登録（**ビルドのステップには渡さない**。`scripts/check_build_env.mjs` の理由と同じ）
- 書き出し先の決定（Actions アーティファクト / 非公開リポジトリ）と保存期間
- 復旧の練習（別の無料 Supabase プロジェクトへ書き戻して、通しプレイが通るか確認する）

**このリポジトリは public** なので、学習者の個人データを含む書き出しを git に平文で置かない。

## 6. 更新のきまり

表の追加・Storage の使いかたを変えたら、この文書の §1 の棚卸しも直す。
バックアップを入れたら §0 の結論を書き換える（「動いていない」を残さない）。
