# 授業前チェック（Cloudflare と Supabase）

授業の 前に **機械が** 通す 検査と、**人にしか できない** ことを 分けて 置く。
学習者にも 先生にも 動作確認を させない（AGENTS.md「検証（引き算まで）と報告」）。

作った きっかけ: 2026-09-02 の 授業中に Error 1102 が 出た。直したあと
「30本 同時アクセスで 1102 ゼロ」と 報告したが、**それは ログインして いない
アクセスで、ログイン画面へ 転送されただけ**だった —— 教材の 処理を 1つも 通って
いない。**匿名の 転送を 合格と 数えない。** それが この 文書の いちばんの 目的である。

---

## 1. 合格の 線

| 検査 | 合格の 条件 | いま | どうやって |
| --- | --- | --- | --- |
| 本番DBの 反映 | 未反映の 移行SQL 0件 | **合格**（14/14） | `node scripts/check_migrations.mjs`（鍵が 無ければ コネクタ） |
| RLS 許可・拒否 | 他人の 閲覧・更新が 拒否され、本人の 保存だけ 成功 | **合格**（13項目） | `node scripts/check_rls.mjs` |
| ログイン済み 30人 | 教材の 中身が 30本 とも 返る | **未実施**（借りる Cookie が 要る） | `SB_COOKIE=... node scripts/load_class.mjs --n 30` |
| Cloudflare | 1102・exceededCpu・5xx が 0件 | 授業中に 見る | `node scripts/watch_class.mjs` |
| Worker CPU | 代表 5ms 未満・最大 8ms 未満（上限 10ms） | 授業中に 見る | 同上 |
| Supabase | 401・403・429・5xx が 0件 | 授業中に 見る | 下の §5 |
| 障害時 | Supabase を 止めても 画面が 固まらない | **未実施** | 下の §4 |

## 2. 本番DBの 反映（済）

`supabase/migrations/*.sql` 14本 ぜんぶが 本番の
`supabase_migrations.schema_migrations` に 入って いる（2026-09-03 に コネクタで 確認）。
**DB は 遅れて いない。**

ただし **自動で 確かめられない**。「デプロイ（DB）」ワークフローは 4回 とも 失敗して
おり、原因は `SUPABASE_DB_URL` が GitHub の Environment「Preview」に **無い**こと。
いまは 人（または AI の コネクタ）が 見ないと 分からない。

→ §6「人にしか できない こと」

## 3. RLS の 許可・拒否（済）

`supabase/tests/rls_check.sql` を 本番に 流して 13項目 ぜんぶ 通った（2026-09-03）。
**ぜんぶ 1つの トランザクションで 走り、最後に `rollback` する**ので 何も 残らない
（流したあとに 行数が 変わって いない ことも 確かめた）。

確かめた こと（管理者で ない 学習者に なりすまして）:

- 許可 … 自分の `quiz_results` 110件が 見える／自分の `profiles` 1件だけが 見える
- 拒否 … 他人の `quiz_results`・`profiles`・`personality_results`・`meeting_turn_logs`・
  仲間で ない `quest_saves` が **1件も 見えない**
- 拒否 … 他人の `quiz_results`・`profiles` を **書きかえられない**（0行）
- 拒否 … 他人の `profile_id` で **保存できない**（42501 row-level security violation）
- 教材 … `studio_contents` は **公開ぶん 4件だけ**（全7件中）
- 匿名（ログインして いない）… 学習者の 表は **ぜんぶ 0件**、教材は 公開ぶんだけ

表は 19個 とも RLS が 有効。ポリシーの 形は `auth.uid() = profile_id` か
`is_admin()`（管理者は 全部 見える —— これは 意図した 動き。名簿と 成績を 見るため）。

### まだ 直して いない 注意（Supabase の 診断 9件・error 0 / warning 9）

1. `is_admin()`・`register_profile_on_signup()`・`enforce_profile_identity()` が
   **ログインして いない人からも 呼べる**（`SECURITY DEFINER` ＋ `/rest/v1/rpc/`）。
   いまは 実害を 確かめて いない。**EXECUTE を 取り上げる**のが 筋。
2. `quest_member_key()` の `search_path` が 固定されて いない。
3. Supabase Auth の「漏れた 合言葉の 拒否」が 切れて いる。

どれも `warning` で、**他人の データが 読める 類では ない**（上の 検査で 確かめた）。
移行SQL 1本で 直せる ので、教材ページを ブラウザ側へ 移す 前に 片づける。

## 4. ログイン済み 30人（未実施）

### なぜ まだ できて いないか

ログインは **Google だけ**（`src/components/title-screen.tsx`）。合言葉での
自動ログインが 無いので、30人ぶんの ログインを 機械で 作れない。
検証用の アカウントを 作るのも、合言葉を 預かるのも AI の 仕事に しない。

### 代わりに できる こと（Cloudflare を 見るには これで 足りる）

Cloudflare から 見れば **30人でも 同じ 人の 30本でも 混みぐあいは 同じ**。
だから **ログインずみの Cookie を 1つ 借りて 30本 同時に 投げる**。

```bash
SB_COOKIE='sb-xxxx-auth-token=...' node scripts/load_class.mjs --base https://staging-academy.nexmax.workers.dev --n 30
```

`scripts/load_class.mjs` は **200 で 教材の 中身が 返った ことまで 見る**。
307（ログイン画面へ 転送）は 数えず、Cookie が 無ければ そもそも 走らない。

### 保存（Supabase 側）の 30本は 別に する

保存を 30回 走らせると **本物の 学習記録が 30行 増える**。検証用アカウントで
`/kaisha/quiz-kaisha_houkoku` を 通しで 1回 やり、`quiz_results` の 増え方を
コネクタで 数える（授業前に 1人ぶんで 十分。同時性は 上の 30本で 見て いる）。

### 障害時（Supabase を 止める）

ブラウザの 開発者ツール → Network → `*.supabase.co` を ブロック して、
教材ページを 開く。**画面が 出て、読める**なら 合格（保存だけ できない）。
いまの 作りでは 教材は 作りおきから 出るので 止まらない はずだが、確かめて いない。

## 5. 授業中の 見張り

```bash
node scripts/watch_class.mjs --every 60
```

`outcome` と `exceptions` を 見る。**数字（cpuTime）だけを 見ない** ——
665ms が ok で 通った ことが あり、それを 根拠に「上限は CPU では ない」と
誤った 結論を 出した（docs/deploy.md §0.12 → §0.13 で 訂正）。
無料枠は バーストを 見逃すので、`outcome=exceededCpu` が 正である。

Supabase 側は コネクタの ログ照会で 見る:

```sql
select log_attributes['status'] as status, log_attributes['error_code'] as err, count(*) as n
from logs where source = 'auth_logs' group by 1, 2 order by n desc
```

直近24時間の 実測（2026-09-03）: 200 が 115件・302 が 4件・400 が 1件
（`refresh_token_not_found`）。**429（回数制限）は 0件。**
教室の 共通IP で 制限に 触れた 記録は いまの ところ 無い。

## 6. 人にしか できない こと

| やる こと | なぜ AI が できないか |
| --- | --- |
| `SUPABASE_DB_URL` を GitHub の Environment「Preview」に 登録する | 接続情報（合言葉入り）を AI が 扱わない |
| 検証用アカウントを 1つ 作る（Google） | アカウント作成を AI が しない |
| 授業前に その アカウントで ログインし、Cookie を 自分の 手もとで 環境変数に 入れる | 同上 |

### いちばん 楽な やりかた（2026-09-03 に 用意した）

```
node scripts/register_db_secret.mjs <project-ref>
```

ホスト名も 置き場所も 機械が 埋める。人が 打つのは **DBの 合言葉だけ**で、
それは **画面に 出ず・ファイルにも 残らず**、`gh` の 標準入力へ 直に 渡る。
`@` や `/` が 入って いても 壊れないよう 百分率エンコードする。

ホスト名だけ 知りたい ときは `node scripts/find_db_host.mjs <project-ref>`。
**合言葉を 送らずに**「この プロジェクトは そちらですか」と 32個の プーラーに 聞いて、
答えた 1つを 返す（ダッシュボードに ログインしなくても 分かる）。

### 手で やる ばあい

登録の 場所: リポジトリ → Settings → Environments → **Preview** → Add secret
（リポジトリ直下の Secrets では **見えない**。docs/deploy.md §0 罠6）。

値は Supabase の ダッシュボード 上部 **Connect** → **Session pooler** の 文字列。

> **「URI」を 選ばない。** あれは 直結（`db.<project-ref>.supabase.co`）で、
> そのホストは **IPv6 しか 持たない**（A レコードが 無い）。GitHub の ランナーは
> IPv4 なので、**鍵は 入ったのに「つながらない」で 落ちる**。
> 見わけかた: 文字列に `pooler.supabase.com` が 入って いて、**`:5432`** で
> 終わって いれば 正しい（`:6543` は Transaction pooler で、移行SQLは 流せない）。
> 形は `scripts/lib/db_url.mjs` が つなぐ前に 見張る。

登録が すんだら、以後は 自動に なる:
「デプロイ（DB）」ワークフローが `integration` への 移行SQL を 流し、
`check_migrations --strict` が 本当に 入ったかを 確かめる。
`node scripts/check_rls.mjs --strict` も 同じ 場所に 足せる（6行）。

## 7. 戻しかた（ロールバック）

### いちばん 速い（Cloudflare の 版を 戻す・1分）

```bash
npx wrangler deployments list
```

で ひとつ 前の Version ID を 見て、

```bash
npx wrangler rollback <version-id> --name academy -m "授業中の 1102 のため" -y
```

**コードも DB も 触らない。** 授業中に 1102 が 出たら まず これ。

### git を 戻す（次の デプロイにも 効かせる）

```bash
git revert <コミット> && git push origin main
gh workflow run deploy.yml -f target=production
```

`main` を 戻したら **`integration` へ 戻しマージする**（忘れると 次の 昇格が
「早送りできません」で 止まる。AGENTS.md「統合とデプロイ」）。

### DB は 戻さない

移行SQL は「いま 動いて いる コードを 壊さない 変更だけ」（列を 足す・not null を
外す）に して あるので、コードを 戻しても DB は そのままで よい。
これが 守られて いる かぎり、戻す 手が 1つで すむ。
