# 制約台帳（constraints）

ユーザーが口頭で伝えた**製品・運用上の制約と好み**の永続台帳。
どのスレッド・セッションも**作業前にこのファイルを読む**（AGENTS.md 多スレッド運用ルール参照）。

**追記のルール**: ユーザーが会話で制約・好みを口にしたら、その場でここに1行追加して
コミットに含める（「前に言ったのに別スレッドに伝わっていない」を無くすため）。
日付と一言の背景を添える。既存項目と矛盾したら、古い方を打ち消し線で残して更新する。

## 運用の制約

| 制約 | 背景・出典 |
| ------------------------------------------------------------------ | ------------------------------------------ |
| 確認依頼は「URL＋操作＋見るポイント」形式。散文で依頼しない | 2026-08-05 運用提案 v1.1 |
| 保存を伴う実機検証は検証専用アカウントで行う | 2026-08-04 本番データ上書き事故の再発防止 |
| staging・本番の更新は main からのみ | 2026-08-03〜05 staging相互上書き事故の再発防止 |
| **ユーザーは PR・マージをしない（クライアント方式）**。AI が検証 → PR作成 → マージ → STG 更新まで進め、ユーザーは **STG のURLで確認するだけ**。OK が出たら AI が本番へ上げる | 2026-08-11「私はクライアント。満足できるものをstgに。OKなら本番。私はPRをしない」 |
| AI の実機通し（ログインを含む検証）は Chrome（Claude for Chrome）で行う。ログインは実アカウントの選択のみ・認証情報の入力はしない | 2026-08-11「AIの通しはchromeでやってほしい」 |
| **ローカルでの実機検証をしない**（`npm run dev` を検証目的で立てない。マシン負荷のため）。検証はブランチ確認URL／STG で行う | 2026-08-11「ローカルサーバーの負荷がかかって困っている」 |
| ユーザー確認を求める前に、**ユーザーが見られる形（ブランチURL/STG）まで進め、fable/Codex のチェックを先に通す**。ユーザーが確認できない中間物で承認待ちしない | 2026-07-28 に同文で2回矯正。「私の確認が必要になるまでは必ず進めるように」 |
| **デプロイ作業をユーザーにやらせない**（「この コマンドを 実行してください」と返さない）。鍵が無くて実行できないなら、鍵の要らない道（GitHub Actions の `デプロイ` ワークフロー）を先に作る | 2026-08-14「私にやらせないで。やらせる場合はそのルールに問題ある」。STG は main への統合で自動、本番は Actions から手動で出す |
| AIのコミットは **`tomy1031` 名義＋`Co-Authored-By: Claude …` の付記**でそろえる（`git config user.email` は `33148568+tomy1031@users.noreply.github.com`）。名義がそろっていないと GitHub Actions の実行が「承認待ち（action_required）」で止まり、ユーザーに Approve を押させることになる | 2026-08-16「Aかな？承認はせず動くように設定」。他セッションはこの形で動いている |
| **ユーザーは動作確認をしない**。通しの確認は CI が自動でやる（アプリは Supabase 未設定なら**鍵ゼロのデモモードで起動する**ので、CI が毎回アプリを立てて6教材を通しプレイできる）。ユーザーが見るのは STG の**中身**だけ | 2026-08-16「これらの動作確認は私はしたくないので、今後しなくて済む方法を」 |
| Live対話の検証用 `GEMINI_API_KEY` は **GitHub の Environment Secrets（環境名 `Preview`）**に置く。使うのは **Playwright を走らせるステップだけ**で、**`.env` に書かない・ビルドのステップに渡さない**（OpenNext が `.env*` をバンドルへ焼き込むため。`scripts/check_build_env.mjs` が検査）。学習者の BYOK 方式は変えない | 2026-08-16 ユーザーが登録。鍵は localStorage 経由で学習者と同じ経路を通る（`src/lib/profile.ts`） |
