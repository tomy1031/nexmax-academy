## 0. なぜ変えるのか

現行（v2）は 4軸のスコア合戦で、**一番高い軸1つ**をタイプにしている。ここに2つの問題がある。

1. **結果が4通りしかない。** 20人のクラスなら平均5人が同じキャラになる。「自分だけの結果」にならず、見せ合う楽しさが出ない。
2. **「はい／どちらでもない／いいえ」が はい に偏る。** 「人の話を聞くのが好きですか」に「いいえ」と答える学生はほとんどいない。全員が heart 寄りになり、**個性の差が出ないままチーム分けの材料になってしまう**。

v3 は MBTI の4軸をそのまま20問（4軸×5問）に載せ替え、**2択の強制選択**にする。これで結果は16通りになり、はい偏りが消える。

**そして今の4キャラは捨てない。** ケルシーの4気質が現行4タイプとそのまま一致するので、4色を「家族」に昇格させる（§1.2）。色・立ち絵・マップの世界観は無傷のまま 4 → 16 に広げられる。

### 0.1 理解設計（作る前の3行）

1. **前提**: 学生は「性格診断」というものを知っている。SNSで MBTI を見たことがある学生も多い。
2. **新情報**: 一度に入れる新概念は「**あなたは “組” と “タイプ” の2段で決まる**」の1つだけ。4軸の名前は結果画面まで出さない。
3. **つまずき予測**:
   - 2択のどちらも自分に当てはまる／当てはまらない → 「**あなたに ちかいのは、どっちですか?**」と設問文に書く。正解を選ぶ場面ではないと明示する。
   - 3対2の僅差で決まったタイプに納得できない → 結果画面に**近い差の軸だけ**「どちらも あなたの いい ところです」と出す（§4.3）。
   - 16も覚えられない → 学習者が覚えるのは**自分の1つと、家族4つ**だけ。他15タイプは一覧で眺める対象にとどめる。

## 1. タイプ体系

### 1.1 4つの軸

学習者に見せる呼び名は、MBTIの専門語を使わず**行動で書く**。英字（E/I等）は結果画面の小バッジにだけ出す。
**極の呼び名は、その下の説明文と同じ語を使う**（呼び名が説明文で自己解説される形にする。未知語を新しく増やさない）。

| 軸 | 記号 | 学習者向けの呼び名 | 左の極 | 右の極 |
|---|---|---|---|---|
| 1 | E / I | どんな とき、元気に なる? | **そとで 元気**（E）人と 話すと 元気に なる | **ひとりで 元気**（I）ひとりの 時間で 元気に なる |
| 2 | S / N | なにを 見て いる? | **いま**（S）目の 前の こと・目で 見える こと | **アイデア**（N）これからの こと・ふと 出て くる かんがえ |
| 3 | T / F | きめる とき、なにを 見る? | **りゆう**（T）りゆうが 合って いるか | **きもち**（F）みんなが どう 思うか |
| 4 | J / P | どう すすめる? | **けいかく**（J）先に きめて すすめる | **そのとき**（P）その ときに えらぶ |

- **どちらが良い・悪いは無い。** 画面のどこにも優劣を書かない（06 §2 と同じ規律）。
- 内部の軸IDは `ei` / `sn` / `tf` / `jp`。
- **不採用にした呼び名と理由**（再提案を防ぐために残す）: 「でどころ」「ものさし」「すじみち」はN1の複合語・慣用で意味が推測できない。「フットワーク」は和製英語で、英語の footwork（足さばき）とずれるため、**カタカナ＝英語という学習者最大の手がかりが逆に誤解を生む**。

### 1.2 4つの家族（既存4タイプを昇格）

| 家族ID（内部・既存流用） | 学習者向けの呼び名 | MBTI | 色 | 家族の性格 | 所属タイプ |
|---|---|---|---|---|---|
| `leader` | まもり組 | SJ | 空色 `#4fa8e8` | ていねい・じゅんばんを きめる・まかせて もらえる | ISTJ / ISFJ / ESTJ / ESFJ |
| `idea` | かんがえ組 | NT | 若葉 `#58c273` | なぜ?・しくみ・つくる | INTJ / INTP / ENTJ / ENTP |
| `heart` | きもち組 | NF | 桃色 `#f26fa7` | 気が つく・人と 人を つなぐ・元気に する | INFJ / INFP / ENFJ / ENFP |
| `challenge` | うごき組 | SP | 金色 `#ffc93c` | やって みる・すぐに 動く | ISTP / ISFP / ESTP / ESFP |

**「〜組」の読みは連濁で「ぐみ」**（まもりぐみ）。学習者は「くみ」と読んでUI音声とずれるため、4家族すべて読み辞書に登録する。

**家族IDは `leader` / `idea` / `heart` / `challenge` のまま変えない。** 既存の立ち絵8枚（`types/{id}.webp`・`{id}_f.webp`）・色トークン・マップの配色をそのまま流用できるため。学習者向けの呼び名だけ「まもり組」等に変える。
判定式は `SJ→leader` / `NT→idea` / `NF→heart` / `SP→challenge`（S かつ J なら まもり組、など。E/I と T/F は家族に影響しない）。

### 1.3 結果の見せかた（2段）

> **あなたは 「まもり組」の まとめの ネクマックス です。**  `ESTJ`

**「おすすめタイプ」「あなたに あう ネクマックス」の枠組みは使わない。** 診断の うれしさ と 見せ合いたさ は
「私は ESTJ！」という自己同一化から生まれる。相棒を推薦する言い方にすると、その動機を直接削ぐうえ、
同じ画面の「あなたは こんな 人」と主語が割れる。

家族＝既存の立ち絵（色つき・性別反映）、タイプ＝エンブレム＋呼び名。この2段構えにすると、**16通りでも学習者が迷子にならない**。
ダッシュ（——）は使わない。N4学習者は「の」で修飾が終わると予測するため、その直後の記号で文の切れ目を見失う。

## 2. 16タイプ台帳

各タイプの `分析` は結果画面の ✓4行（05 §2.2 の形式を踏襲）。最後の1行は必ず「日本の IT の しごとでは〜」で締める。
`チーム役割` は §6 の編成と、学習者向けの「チームで あなたが とくいな しごと」の両方に使う。

**文言のきまり**（16タイプすべてに適用。N4学習中の学生を基準にする）:

- `ひとこと` は**述語で終える**（「〜します」）。体言止めの断片は、N4学習者に「文が途中で切れている＝自分が読めていない」と感じさせる。
- **1文の未知語は1語まで。** 特に4行目（結果画面で最も読ませたい一文）に未知語を2語以上入れない。
- **「かつやく」「力を はっき」「たよりに されます」を締め文に使わない。** 旧案は16タイプ中10タイプがこの3表現で終わっており、どのタイプを引いても最後の一文が読めない状態だった。
- **擬態語・畳語副詞を使わない**（きちんと・はっきり・じっくり・つぎつぎ・さっと・まっすぐ）。読みが分かっても意味が出ないため、ふりがなでも語彙メモでも救えない。
- **交ぜ書きを使わない**（手じゅん・目ひょう・てい案・気ぶん・まん中）。漢字語としてもかな語としても記憶に残らず、読み辞書にも登録できない。**漢字＋ふりがな＋語彙メモ**（§2.5）にする。
- **むずかしい語をひらがなに開かない。** 開いても意味は出ないので解決にならない（§2.5）。漢字で書き、ふりがなを合成し、語彙メモで意味を出す。
- **表記を統一する**: 「きもち」「かんがえる」「気が つく」「提案」。同一ブロック内での表記ゆれを禁止する。
- 職場語（対応・運用・仕組み 等）は**平易語に置き換えず、§2.5 の語彙メモで支える**（01ガイド R6-1: 実務語彙の平易語化は違反）。

### 2.5 語彙メモ台帳（§1〜§5 の学習者向け文言で使う職場語）

**なぜ必要か**: 01ガイド R6-1 は実務語彙の平易語化を違反としている（「要件定義」→「決めること」は不可）。一方でN4学習中の学生には、むずかしい語は読めても意味が出ない。**「残す」と「読める」を両立させる唯一の方法が語彙メモ**なので、v3で機構ごと入れる。

#### ひらがなに開いても解決しない

v3の初版は職場語を全部かなで書いていた。しかし **「うんよう」と書いても、意味を知らない学生には意味ゼロの4拍でしかない**。むしろ漢字が消えるぶん、意味の手がかりが減って悪化する。同じ理由で交ぜ書き（手じゅん）も不可。

そこで表記の方針を次の3層にする。

| 層 | やること | ねらい |
|---|---|---|
| 1 | 本文は **漢字＋ふりがな** で書く。N4を超える漢字でもよい | 読める。かつ漢字が意味の手がかりになる |
| 2 | 語に点線の下線。ホバー／タップで **やさしい日本語の意味** | 日本語のまま理解させる |
| 3 | 同じポップオーバーに **英語** を添える | 日本語で届かなかったときの非常口 |

**英語は本文には出さない。** 学習者に英語を読ませたいのではない。日本語で詰まった1語のために画面全体をあきらめさせないための最後の受け皿として、ポップオーバーの中にだけ置く。

##### 吹き出しは 日本語 → 英語 → 日本語の意味 → 英語の意味 の4段

初版は「日本語 → 日本語の意味 → 英語の説明」の3段だった。しかし**まだN4を勉強中の学習者は、やさしい日本語の説明そのものが読み切れないことがある**。3段目まで読まないと英語に届かない構成では、いちばん助けが要る学習者がいちばん遠回りをする。

そこで **対訳の1語（`englishTerm`）を説明より先**に置く。

| 段 | 内容 | 誰のための段か |
|---|---|---|
| 1 | 日本語（漢字＋読み） | いま画面で見ている語との対応を取る |
| 2 | **英語1語** | ここで足りた人は説明を読まずに設問へ戻れる |
| 3 | やさしい日本語の意味 | 日本語のまま理解したい人 |
| 4 | 英語の意味 | 1語では足りず、日本語の説明も届かなかった人 |

`englishTerm` は**説明ではなく見出し**。長い英文を入れると「ことばメモ」のチップが1行に収まらず、2段目の役目（短く見て済ませる）も果たさなくなる。20文字以内・句点やダッシュを含まないことを `tests/glossary.test.ts` で固定してある。

**意味メモに擬態語を使わない。** 意味メモはむずかしい語から逃げてきた先なので、そこに「どきどき」「しっかり」のような読めても意味の出ない語があると行き止まりになる。禁止語として機械検査の対象にしてある。

##### 閉じ方はホバーを外すこと（マウス）／もう一度タップすること（タッチ）

マウスの端末ではホバーで開き、**外すと閉じる**。読みたい語の上に置くだけで出るので、設問を読む流れが切れない。

タッチ端末で同じことをすると、タップで `mouseenter` → `click` の順に発火して**開いた直後に閉じる**。そこで `matchMedia("(hover: hover)")` で端末を見て、**ホバーとタップのどちらか一方だけ**を効かせる。キーボード操作にはフォーカス／ブラーを割り当てる。

**ふりがなは読み辞書に依存させない。** 下線を引く語こそ一番むずかしいので、`PERSONALITY_RESULT_READINGS` に登録し忘れた瞬間に裸の漢字が出る。`GlossaryText` は台帳の `reading` を読み辞書の先頭に足してから合成し、辞書漏れでもルビが出るようにする。

**UI**: 薄い点線の下線 → ホバー／タップで4段のポップオーバー。**性格診断の中では 1文に2語以上は下線を引かない**（同じ文で2回タップさせない。該当したら文を分ける）。データは `src/content/glossary.ts` に `{ term, kanji, reading, meaning, englishTerm, englishMeaning }` で持ち、読み辞書（`readings`）とは別物として扱う。

##### この「1文1語」は性格診断だけの決まり（2026-08-31 に範囲を絞った）

教材の本文（`DictionaryText` / ことばの正 600語）も、この節を引いて1文1語にしていた。しかし本文はむずかしい語が**1文の中にかたまって**出る。「観光DXで、カンボジアの 町の 物語を 動画に したいです。」で引けるのが1語だけでは、**辞書に載っているのに引けない語**が残る（2026-08-31 の指摘「辞書が足りていません。DX・物語・動画・チャットボット」）。

そこで**教材の本文は当たった語ぜんぶに下線を引く**（`findDictionaryTerms`）。のせるだけで意味が出る仕組みなので、下線が増えて読む手が止まることはない。

診断は1文1語のまま残す。理由は「2回タップさせない」ではなく**代わりの受け皿があるから**——Ⓐ/Ⓑ が `<button>` で下線を置けないぶん、設問カードの下の「ことばメモ」の帯（§3.0.1）がその画面の語をぜんぶ並べている。本文にはその帯が無い。

**置ける場所とそうでない場所**: 質問の柱書きは `<p>` なので語彙メモを置ける。**Ⓐ/Ⓑ の選択肢は `<button>` の中なのでボタンを入れ子にできず、ルビだけ**。選択肢に未知語を置かないこと（そこだけ救えない）。

**吹き出しの位置**: 上に出すのが既定だが、画面の上のほうにある語（質問の柱書きなど）では上に出すと画面外に切れて何も見えない。開くたびにボタンの位置を測り、上に余白が無ければ下に出す。左右も画面のふちからはみ出さないように寄せる。

### 3.0 20問の前に出す導入

**「性格」という語自体を知らない前提で書く。** 学習者は「せいかく」を辞書で引いても
「character / personality」のような抽象語に着地し、何を聞かれているのか分からないまま
20問に入ることになる。だから **具体（人には すきな やりかたが ある）を先に渡してから、
その具体に語を当てる**。語から入らない。

文言は `PERSONALITY_INTRO`（`src/content/personality.ts`）に置く。**コンポーネントに
直書きしない** — 直書きすると禁止語検査からも語彙メモの網羅検査からも漏れる。
実際、初版でこれをやったために「性格」「診断」が語彙メモに載っていないまま画面に出ていた。

1. 人は みんな、すきな やりかたが ちがう
2. はやく きめる 人も、ゆっくり かんがえる 人も いる。**どちらも いい**
3. その いつもの やりかたを 性格と 言う。それを しらべるのが 性格診断
4. 20の しつもんに 答えると、じぶんの すきな やりかたが 見えて くる
5. おわると、にた ネクマックスが 1人 出て くる

「正しい 答えは ありません」とは書かない——正誤の枠組みを持ち込まないため（§10）。

### 3.1 出題の作法

- **1問ずつ表示。左右に2枚の場面カード（Ⓐ／Ⓑ）を並べる。** 回答すると次の問へ横スライド、「← もどる」で回答を保持したまま戻れる。
- 全問共通の問いかけは「**あなたに ちかいのは、どっちですか?**」。**正解を選ぶ場面ではない**ことを毎問の画面で示す。
  - 旧案「どちらかと いうと、どっちですか?」は不採用。**アプリ中で最も露出の多い文字列**がN2の固定表現で、分解しても意味が合成できない。丁寧体「どちら」と口語「どっち」の文体不統一もある。
- **各問の柱書きは、それ自体で完結した文にする。** 「〜のは」で終わる断片は、Ⓐ／Ⓑと頭の中で連結して初めて文になるため、語彙とは別の読解負荷が乗る。状況文（「〜ました。」）か疑問文（「〜ですか。」）のどちらかで終える。
- **選択肢ⒶとⒷの難易度を揃える。** 片方だけ難しいと、意味の分からない側を避けて易しい側に流れ、**選択肢の難易度差が新しい偏りを作る**（2択にして「はい偏り」を消した意味がなくなる）。
- 出題順は軸をローテーション（EI → SN → TF → JP を5周）。
- **Ⓐが常に同じ極にならないようにする。** Ⓐ／Ⓑがどちらの極に入るかは問ごとに入れ替えてあり、**§3.2 の表が正**（EI・TFは2・4問目、SN・JPは1・3・5問目でⒶが反対側）。どちらの極かはデータ（`a.pole` / `b.pole`）が持ち、表示順に意味はない。
- 言語トグルは現行のまま3つ:「やさしい日本語」（分かち書き・既定）／「日本語」（通常表記＋ふりがな）／「English」。
- 進捗は「**20もんの うち n もんめ**」＋ドット20個。20問目の回答後に「けっかを 見る」。
  - 旧案「n / 20 もんちゅう」は不採用。「〜中（ちゅう）」＝「〜のうち」の漢語接尾辞は未習で、「もんちゅう」が一語の未知語に見える。
- 場面は**しごとの場面**に寄せる。診断そのものが職場語彙のインプットになる（01ガイド「日本語と仕事を分けない」）。

## 4. スコアリングと判定

### 4.1 計算

- 回答は `"a"` または `"b"`。選ばれた側の**極に1点**。「どちらでもない」は無い。
- 各軸5問なので、**軸の合計は必ず5点**。E+I=5、S+N=5、T+F=5、J+P=5。
- **奇数なので同点が構造的に起きない。** タイブレークのルールは不要になる（v2の `heart > challenge > idea > leader` は削除）。
- 保存する `scores` は4キー。値は**左の極（E / S / T / J）側の点数**（0〜5）。右の極は `5 - 値` で出る。

```ts
scores = { ei: 4, sn: 1, tf: 3, jp: 5 }
// → E=4/I=1, S=1/N=4, T=3/F=2, J=5/P=0 → ENTJ → 家族 idea（かんがえ組）
```

- タイプコード: `ei>=3 ? "E":"I"` + `sn>=3 ? "S":"N"` + `tf>=3 ? "T":"F"` + `jp>=3 ? "J":"P"`。
- 家族: `S && J → leader` / `N && T → idea` / `N && F → heart` / `S && P → challenge`。

### 4.2 かたよりの強さ

`|値 - 2.5|` が大きいほどその軸の傾向が強い。5-0 と 3-2 を同じ扱いにしない。

| 点差 | 表示 |
|---|---|
| 5-0 / 4-1 | **これが あなたらしい ところ** |
| 3-2 | **どちらも あなたの いい ところ** |

節見出しの「かたより」はN1のため**UIラベルには出さない**（実装者向けの呼称）。画面に出す場合は「あなたらしさの つよさ」。
旧案「はっきり その 傾向」は不採用。「傾」はN2漢字でふりがなも無く、**§10 の自己チェック「学習者向け文の漢字はN4まで」に本書自身が違反していた**。加えて副詞が名詞を修飾する非文的な構造だった。

### 4.3 僅差の見せかた（決めつけない）

3-2 で決まった軸だけ、結果画面の下に1行出す。軸の呼び名は §1.1 と同じ語を使う。

> 「りゆう」と「きもち」は、どちらも あなたの いい ところです。ときに よって、りょうほう つかって いますね。

軸が2つ以上 3-2 なら、**EI→SN→TF→JP の軸順で最初の1つだけ**出す（画面を重くしない）。**「あなたは本当は◯◯かもしれません」とは書かない**——診断の結果を疑わせない。

## 5. 相性（学習者向け）

**方針**: 相性の悪いペアは作らない。**どの組み合わせにも、必ず前向きな意味を与える。** 学生同士の人間関係に直接影響するため、ここは文言設計を最優先する。

### 5.1 2種類だけ出す（選定は決定的）

| 種類（内部呼称） | 学習者向けの見出し | カード（各2枚・この順で固定） | 説明文 |
|---|---|---|---|
| にて いる | **すぐに 話が できる なかま** | ① **E/Iだけ**ちがうタイプ ② **J/Pだけ**ちがうタイプ | すこしの ことばでも、わかって もらえます。 |
| たすけあえる | **じぶんに ない ものを もって いる なかま** | ③ **4つ全部**ちがうタイプ ④ **S/NとT/Fの2つだけ**ちがうタイプ | 見て いる ところが ちがうので、二人が いると チームが もっと よく なります。 |

- 4枚は上のルールで**一意に決まる**（乱数・表順への依存なし）。自分自身のタイプはカードに出さない。
- 各カードに理由の1行を添える（例: ①「元気に なる ときだけ ちがう」④「見て いる ところと、きめる ときに 見る ものが ちがう」）。
  ③の理由に「見て いる ところ」を使わない——それは §1.1 の**SN軸の呼び名**なので、全体の比喩に流用すると
  ③を「SNだけ ちがう相手」と誤読させる。「4つ とも ちがう」と書く。
- **載らない11タイプの受け皿を1行置く**:「ここに ない タイプとも、いい チームに なれます。」
  学生は必ず友達と結果を突き合わせる。4枚だけに前向きな意味を与えると、**空白が「相性がよくない」と読まれる**——
  §5 が防ぎたかったのはまさにそれ。
- **「合わない」「にがて」「気をつけて」は書かない。**（01ガイド禁止語の精神）
- 見出しの主語は必ず「なかま」。「相性が悪い相手」という枠組みをUIに一切登場させない。
- 旧案の見出し「つうじる」「おぎなえる」は不採用。**本節は「文言設計を最優先する」と宣言しているのに、その見出しの動詞がN2慣用（話が通じる）とN1＋可能形（補える）で最も読めない**という逆転が起きていた。

### 5.2 チームで とくいな しごと

自分のタイプの `チーム役割`（§2）を、結果画面に1行で出す。

> チームで あなたが とくいな しごと: **だんどり役**
> しごとの じゅんばんを きめる。

「光る しごと」は不採用（「光る」の比喩用法は文学的で、字義「光を出す」で読まれる。しかも生漢字でふりがな無しだった）。ダッシュ（——）も使わない。
`だんどり` `しあげ` は職場語として残し、§2.5 の語彙メモで支える。**推測不能だった `きりこみ役` `ばづくり役` は言い換え済み**（「きりこみ」は辞書を引くと「切れ目・切り口」に着地し、**辞書が誤誘導する**最悪のケースだった）。`こだわり役` は「拘る」に否定的語義があり §5 の前向き原則と衝突するため `ていねい役` に変更した。

## 6. チーム編成 v2（教師向け）

現行 `createBalancedTeams`（型のラウンドロビン）を、**評価関数つきの編成**に置き換える。教師画面なのでふりがな不要。

### 6.1 チーム数と定員

- チーム数 = `ceil(人数 ÷ 指定サイズ)`（指定サイズは現行どおり 2〜6）。
- 定員は**均等割り**: 基本 `floor(人数 ÷ チーム数)`、余りの人数分だけ先頭チームから +1。**チーム間の人数差は最大1**。配置は定員未満のチームだけを候補にする（定員超過は起きない）。

**1人チームは生じうる。** 指定サイズ2で人数が奇数のとき（n=5 なら `[2,2,1]`）、2人組に奇数人は割り切れないため数学的に回避できない。式を正典として式どおりに実装し、次の2点で受け止める:

- `TeamSuggestion.isSolo` を立て、**1人チームには「足りない役割」の警告チップを出さない**。1人では J も F も必ず欠けるが、本人に打つ手がないことを突きつけても意味がない。ペナルティ自体は素の値のまま返す（編成アルゴリズムが1人チームを避けようとするために必要）。
- `TeamPlan.notice` に「◯人ずつでは割り切れない人数のため、1人だけのチームが◯つできます。」を入れ、教師が意図した編成だと誤解しないようにする。

クラスの学生が指定サイズ未満（1人しかいない等）のときは、従来どおり `canBuild: false` と `reason` を返す。

### 6.2 ペナルティ関数（重み付き加算・重みが優先度を表す）

チームごとに次を計算し、**全チームの総和**を最小化する。辞書式の優先順位ではなく、重みの大小で優先度を表現する。

| 条件 | ペナルティ |
|---|---|
| 段取り役の不在（`J` が0人） | +8 |
| 気づかい役の不在（`F` が0人） | +8 |
| 家族のかたまり | 家族ごとに `max(0, 人数 − 2) × 4` |
| 同一コードの重複 | コードごとに `max(0, 人数 − 1) × 2` |
| E:I のずれ | `abs(チームのE人数比 − クラス全体のE人数比) × 2` |

### 6.3 アルゴリズム（決定的・乱数なし）

1. 学生を `家族（§1.2の表の順）→ コード（§2の表の順）→ display_name（ja照合）→ id` の固定キーで並べる（最終キーが `id` なので同名でも順序が揺れない）
2. 貪欲法で1人ずつ、定員未満のチームのうち**総ペナルティの増加が最小**のチームへ入れる（同点なら人数の少ないチーム、さらに同点ならチーム番号の小さい方）
3. 全員配置後、固定のインデックス順にメンバー2人の入れ替えを走査し、**総ペナルティが下がる最初の入れ替え**を適用して走査を先頭からやり直す。改善が無くなるか200回適用した時点で終了（最初の改善を採る方式なので決定的）
4. 打ち切りで終わっても結果はそのまま提案として表示する（教師が手で調整する前提。§6.4）

### 6.4 教師画面に出すもの

- チームごとに: メンバー（呼び名＋4文字コード＋エンブレム）・家族の内訳バー・**「このチームに足りない役割: 段取り」**の警告チップ
- 軸スコアは**双極バー**（`E ◀━━●━━▶ I`・中央2.5）で表示する。0〜5の単方向棒は「低い＝弱い」と誤読させるため使わない（06 §2 の規律。`ei=1` は「Eが弱い」ではなく「Iが4」である）
- 編成結果は提案。**教師が手で入れ替えられる**（ドラッグまたは選択して交換）。入れ替え後もペナルティ・警告チップは再計算する

## 8. データ設計（v3への移行）

現在の本番データは **`profiles` 1行（開発者本人）・`personality_results` 0行**。移行の互換性を守る必要はなく、**作り直してよい**。

### 8.1 マイグレーション（順序が重要）

実装は `supabase/migrations/20260727120000_personality_v3.sql`。

1. **v2 の行を削除する。** ただし無条件の `delete from public.profiles;` にはしない——2回目の実行で移行後の本物の学習者データが消えるため。**`personality_type` が16コードでない行だけ**を消す条件付きにする（cascade で `personality_results` も消える。`is_admin` は次回オンボーディング時にトリガーが許可メールから再付与する）。
   （当時）`/welcome` の診断済み判定は**行の存在**（`if (profile) redirect("/map")`）だったので、行を消せば自然に再診断へ入った。旧 `personality_type='leader'` が新CHECK制約に衝突してマイグレーション自体も失敗するため、行削除が必要だったのはそのとおり。

   > **2026-08-03 更新: この「行の存在で判定」は解消済み。**
   > `/welcome` は `isDiagnosisComplete(answers)`（`src/lib/profile.ts`）で判定するようになった。
   > そのため **`answers` と `scores` を空にするだけで再診断へ入れる**（行を消す必要はない）。
   > 詳細は §8.4。
2. 旧CHECK制約（4値）を落とす
3. 新CHECK制約を張る:
   - `personality_type`: 16コードのいずれか（両テーブル）
   - `profiles`: **`answers` と `scores` を1つの制約で見る**。「両方とも空（未診断）」か「両方とも完成」のどちらかに限定する。列ごとに独立して空を許すと「回答は空なのにスコアだけ完成」という中途半端な状態が通ってしまう
   - `personality_results`: 空を許さない（完成した結果しか積まないため）
   - 完成の定義: `answers` は長さ20の配列で全要素が `"a"`/`"b"`、`scores` は `ei`/`sn`/`tf`/`jp` の**4キーちょうど**・各値0〜5の整数（§4.1 の `>=3` 判定は「整数0〜5」をDBが保証して初めて成立する）
4. `personality_version integer not null` を両テーブルに追加。**列追加時だけ default 3 を使い（既存行を埋めるため）、直後に `drop default` する**

**CHECK制約の書きかた**（実装時にハマる点）:

- **PostgreSQLのCHECKにサブクエリは書けない。** `not exists (select ...)` や `count(*)` は使えないので、jsonb演算子だけで表現する（`answers <@ '["a","b"]'` で a/b 以外を弾く、`scores - 'ei' - 'sn' - 'tf' - 'jp' = '{}'` で余分なキーを弾く）
- **CHECKは結果がNULLだと「合格」扱いになる。** キー欠損で `jsonb_typeof(NULL)` → NULL → 素通り、という穴が開くため、型判定は `coalesce(jsonb_typeof(...), '')` で包む
- **`jsonb_array_length` は配列以外でエラーになる。** ANDの評価順は保証されないので `CASE` で順序を固定する
- 値域は `(scores ->> 'ei') ~ '^[0-5]$'` で見る。`3.0`（小数表記）・`6`・`-1`・`"3"`（文字列）をすべて落とせる

その他:

- `personality_version` は **default に頼らず、アプリの insert / upsert が明示的に 3 を書く**（`src/lib/profile-db.ts` の `PERSONALITY_VERSION`）。defaultを残すと version を省略した INSERT が黙って通る。06 の履歴比較（`calculateResultChange`）は version が同じ結果同士だけ比較する。
- **DB変更とアプリ変更は同一リリースで適用する**。現在の利用者は開発者1人のため互換期間は設けない（適用の瞬間の書き込み失敗は許容）。
- localStorage キャッシュは `nexmax.profile.v2` → **`nexmax.profile.v3`**。v1・v2 は読まずに削除。

**行は残るので `personality_results` の受験履歴も残る。**

- `answers` と `scores` は**同じ UPDATE で**空にする。制約が「両方空」か
  「20問そろい」しか許さないため、片方だけだと弾かれる
- **「削除」は別物。** `profiles` 行ごと消すので `personality_results` も
  cascade で道連れになる（不可逆）。やり直させたいだけなら必ずリセットを使う
- マイグレーション不要。既存の `profiles_update_own_or_admin` が管理者に
  全カラムの更新を許しているため、RLS 変更なしで成立する
- **残る制約**: `personality_type` は not null で「未診断」を表す値がないため、
  リセット後も前回のコードが行に残る。画面の判定は `answers` 側なので表示には出ない

### 9.3 フェーズB — 立ち絵32枚（16タイプ × 性別2）

3. `types/{family}_f.webp`（女性の描き分けの正典）

家族色は「参照画像の空色を◯色に置き換え、他はすべて同一に保つ」と指定する。16進で指定するより

#### 受入基準

| 観点 | 落とす条件 |
|---|---|

| 役割 | 装備が上表と違う、または役割が絵から読み取れない |
| 家族色 | 4家族の色が混ざっている（同じ組の4体が同じ色に見えない） |
| 性別 | 男女の差が上表の5点以外に及んでいる（体型・表情の性格づけ等） |
| 透過 | 背景が透明でない、または輪郭の外に不透明な画素が残っている |
| 文字 | 判読できる文字が入っている（胸のMマークだけは可） |

**16体を並べて見る**こと。1枚ずつ見ると気づかないが、並べると色の混線と絵柄のぶれが出る。

#### フォールバック

`NexMaxType` は `{CODE}` → `{family}` → `reference.png` → 絵文字 の順に落ちる。
**32枚が1枚も無くても診断は完成品として動く**（家族立ち絵で従来どおり表示される）。

## 10. 文言規律チェック（実装後に必ず）

- [ ] 「不正解」「間違い」「ダメ」なし。診断に正誤の枠組みを持ち込んでいない
- [ ] 「ぼうけん・たんけん・クエスト・宝」なし
- [ ] 相性に「合わない」「にがて」なし。すべての組み合わせが前向きに書かれている（§5）
- [ ] スコアが低い軸を「弱い」「できない」と書いていない（06 §2 の規律）
- [ ] 学習者向け文の漢字は、**N4を超えるものも可。ただし必ず読み辞書経由でふりがなが出ること**（§2.5）。ルビの無い裸の漢字を残さない
- [ ] **むずかしい語をひらがなに開いていない**。開くのは解決ではない。漢字＋ふりがな＋語彙メモにする
- [ ] **語彙メモの語に英語の意味が入っている**。ただし英語は本文には出さない（ポップオーバーの中だけ）
- [ ] ルビHTMLを手書きしていない（読み辞書＋合成のみ）
- [ ] **読み辞書の並びで短い語が長い語を食べていない**（「手」が「手順」より前に無い）。同位置なら配列で先に出たほうが勝つ
- [ ] **擬態語・畳語副詞が無い**（きちんと・はっきり・じっくり・つぎつぎ・さっと・まっすぐ）。読みが分かっても意味が出ないため、ふりがなでも語彙メモでも救えない
- [ ] **交ぜ書きが無い**（手じゅん・目ひょう・てい案・気ぶん・まん中・せつめい書）。読み辞書に登録できず、漢字語としてもかな語としても定着しない
- [ ] **表記ゆれが無い**（きもち／かんがえる／気が つく／ていあん に統一）。特に同一タイプの4行内での混在
- [ ] **述語で終わっている**（ひとこと16件・設問の柱書き20件・§4.2 の表示2件）
- [ ] **1文の未知語は1語まで**。§2 の4行目16本と、設問の選択肢40件を数える
- [ ] **ⒶとⒷの難易度が揃っている**（片方だけ難しい設問が無い＝選択肢の難易度差による偏りが無い）
- [ ] §2.5 の語彙メモが、学習者向け文言に出るすべての職場語を覆っている
- [ ] `npm run lint:content` / `npm run measure:readability` が通る
