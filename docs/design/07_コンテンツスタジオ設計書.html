1目的と全体像

本書は、Nexmax Academy の教材（ステージとその中のコンテンツ）を Claude Code からも、ブラウザの管理画面からも、同じ規格で作れるようにするための設計である。 新しいページ種別として漫画ページ（4コマ／ストーリー漫画の2形式）とWYSIWYG の説明ページ（ブログ風）を追加し、 どちらの経路でも Codex App Server に「一言の依頼＋2〜3問の回答」だけで 画像込みの完成品まで作らせられるようにする。

1.1 設計の柱（3つ）

柱内容理由
規格は1つ コンテンツの正しさは zod スキーマ（src/content/schema.ts）だけが決める。Claude Code も管理画面も Codex も、全員この契約に従う。 経路が増えても品質検査（禁止語・秘匿漏れ・ID重複・ルビHTML禁止）が1か所で効く。既存の設計方針03 §1 の第一原則をそのまま拡張する。
経路は2つ ① Claude Code：JSONファイルを書いて git → Vercel 自動デプロイ。② 管理画面：ブラウザで編集して Supabase に保存 → 即時反映。 開発者（tomy）は会話で高速に、先生は手元のブラウザで安全に。同一IDは DB 優先で合流させる（§11）。
AIは「工房」 Codex App Server はチャットではなく定型ジョブの工房。下書き生成／画像生成／単語抽出／原稿執筆を、決まった入出力（スキーマ準拠JSON）で行う。 「簡単な依頼→質問に答える→完成」を成立させるには、自由会話でなく構造化された受付が必要（§6）。

2.1 検査の一本化

現在 scripts/lint_content.ts にある検査ロジック（スキーマ・禁止語・秘匿漏れ・ID重複）を src/lib/content-checks.ts に切り出し、CLI と管理画面APIの両方が同じ関数を呼ぶ。

経路検査の入口タイミング
Claude Codenpm run lint:content（CI・pre-commit）コミット時
管理画面POST /api/studio/content がサーバ側で同じ検査を実行保存・公開時
Codex工房bridge が生成直後に同じ検査を実行 → 不合格なら自動修正ループ（最大2回）下書き生成時
決定：AIが生成したものも人間が書いたものも、検査だけを信じる。 「誰が作ったか」でなく「スキーマと機械検査を通ったか」で公開可否を決める。学習者向け文言の規律 （禁止語なし・ルビHTML手書きなし・選択式は読解のみ）はこの層で守られ続ける。

3ステージ規格

現在ハードコードされている src/content/stages.ts の STAGES を、コンテンツ規格上の stage kind に移す。ステージ＝コンテンツの入れ物と順序であり、 マップ（/map）はこのデータから描画する。

単語は別管理・紐づけのみ単語ステージは従来どおり独立した wordstage。ステージは wordStageIds で指すだけ。§9 の抽出ジョブがこの紐を使う。

マップとの接続ピン → ステージ詳細（コンテンツ一覧・順に進むボタン）→ 各教材。既存の「続きから」はステージ内の未完了コンテンツへ直行に拡張。

4漫画ページ（manga）

最重要の設計判断：画像に日本語の文字を焼き込まない。 セリフ・ナレーションはデータとして持ち、HTML レイヤーで画像の下（または上）に描画する。 理由：①生成画像の文字化け問題を根絶（既存スキルでも文字化けQAが最頻出） ②ふりがな合成・ふりがなトグル・禁止語検査がそのまま効く ③あとからセリフだけ直せる（画像の再生成が不要）。

4.0 ふたつの形式 — 4コマとストーリー漫画

同じ manga kind の中で、format フィールドにより2形式を扱う。 データ構造（pages → panels）は共通で、形式の違いは「量」と「レイアウトヒント」だけにする。 エンジンも編集画面も1つで済み、途中で4コマをストーリーに育てることもできる。

format: "yonkoma"（4コマ）format: "story"（ストーリー漫画）
規模1ページ＝縦4コマ。1〜3本複数ページ・章あり。1話 8〜30ページ程度
コマ割り固定（縦に4等分）ページごとに可変。パネルに size ヒント（normal / wide / tall）を持ち、見開き的な「決めゴマ」= wide を作れる
場面転換なし（1本1場面）pages[].title による場面カード（「その日の午後 — 会議室」など）を挟める
読み方縦スクロールで1本ずつ縦スクロール（Webtoon式）。ページ区切りで余白＋「p.3 / 12」表示。しおり（続きから）つき
用途導入のつかみ・1概念1本シナリオ全体の追体験（例：障害発生から報告・復旧までの一日）

ストーリー漫画の制作は2段生成（§6.3）： Codex工房はいきなり全ページを描かず、①あらすじ→場面リスト（ページ数・各場面の学習ポイント）を先に出して先生の確認を取り、 ②承認後にネーム（コマ割りJSON＋セリフ）→ 画像生成、と進む。 長尺で方向がずれたまま30ページ生成する事故を防ぎ、途中の場面だけ作り直すこともできる。

4.1 読む画面（学習者向け）

  • 縦スクロール（スマホ前提）。パネルは画面に入ったらふわっと表示。 size: wide は横幅いっぱい、tall は縦長で「決めゴマ」の間を作る。
  • セリフは吹き出し風のHTMLで表示し、ふりがなON/OFFトグルつき（RubyText を使用）。
  • ストーリー形式の追加要素：場面カード（ページ間の区切り）／「p.3 / 12」の現在地表示／ しおり（進捗保存層に最終到達パネルを記録し「続きから」で復帰。疲れている学習者が分割して読める）。
  • 読み終わり判定＝最後のパネル到達。進捗保存層に記録し、ステージ進捗へ反映。
  • 末尾に「この漫画に出てきたことば」チップ（§9で抽出した語 → 辞書ポップアップ／単語ステージへの導線）。

4.2 編集（管理画面）

  • ページ＝パネルのリスト。並べ替え・挿入・削除はドラッグまたは上下ボタン。
  • 各パネル：画像スロット（生成する／アップロードする／あとで）＋セリフ行の編集。
  • 画像スロットの「生成」は §7 のジョブへ。prompt を保存してあるので「少し直して再生成」が一言でできる。

5説明ページ（article / WYSIWYG）

ブログ風の読み物。保存形式は生HTMLではなくブロックJSONとし、 管理画面のWYSIWYGエディタ（Tiptap を許可ノード限定で使用）はブロックJSONへ相互変換する。 Claude Code はブロックJSONを直接書く。

ブロック内容備考
heading見出し（level 2〜3）目次を自動生成
paragraph本文（プレーンテキスト＋強調のみ）ふりがなは辞書から合成（規律2）
image画像スロット（manga と同じ構造）生成／アップロード／差し替え可
calloutポイント・注意（tone: point | care）ネクマックスのアイコン付き
list / steps箇条書き／手順（番号つき）
vocabことばチップ（語・読み・意味）タップで辞書ポップアップ
link次の教材への誘導カードステージ内コンテンツ限定
生HTMLを許さない理由： ①禁止語・ルビ・秘匿漏れの機械検査がテキストに対して確実に効く ②XSSの心配なくDB由来コンテンツを描画できる ③Claude Code と WYSIWYG の相互編集で壊れない（HTMLの方言問題が起きない）。 表現力はブロックの追加で伸ばす（規格の進化はスキーマ変更＋マイグレーションのセットで行う）。

6Codex工房（CodexAppServer連携）

「ただのチャット」にしない。受付 → 質問 → 生成 → 検査 → 下書き の定型フローで、 先生は一言の依頼と2〜3個のボタン回答だけで画像込みの完成下書きまで到達する。

6.2 bridge は既存の codex_bridge.mjs を拡張する

新しい常駐プロセスは作らない。既存ブリッジ（WS素通し）の設計思想 「トンネルは薄く保ち、賢さはクライアント側に置く」を崩さず、足りないものだけを足す。

項目内容状態
WSトンネルWS /codex → codex app-server（ws://127.0.0.1:17653）へ素通し。app-server の自動起動・状態確認（GET /api/codex/status）つき。npm run codex:bridge実装済（別ブランチ）
ジョブの頭脳受付→質問→生成→検査のオーケストレーションは管理画面側のTypeScript（既存 CodexTransport を拡張した StudioJobs）。bridge にロジックを持たせない新規
アセット搬入口唯一の追加API：POST /api/assets。ローカルで生成された画像・音声を受け取り WebP/圧縮変換して Supabase Storage へ上げ、URLを返す（service key は bridge のローカル env のみが持つ）新規
認可開発時＝loopback のみ。本番＝設計08 §0.1.1 のまま：Cloudflare Tunnel で 8790 を公開し、Access（無料枠）で管理者2人の Google 認証に限定。独自トークン方式は発明しない設計済（08）
鍵の置き場所Codex 認証・先生用 Gemini キー・service key はローカル env のみ。ブラウザ・Vercel には出さない—
不在時管理画面は /api/codex/status 不達を検知したら「おまかせ作成は じゅんびちゅう」を表示。手作業の編集・公開は bridge なしで全部できる—
前提：codex_bridge.mjs・/admin/ai・設計08/09 は claude/character-personality-design-2328fd ブランチにある。本設計の着手前にこのブランチを合流させる（§13）。

6.3 受付プロンプトは共有資産

種別ごとの受付プロンプト（理解設計ガイドの要点・スキーマ・良い例）を docs/studio/prompts/*.md としてリポジトリに置き、 Codex工房と Claude Code が同じものを読む。 これで「どちらの経路で作っても同じ品質基準」が実現する。プロンプトの改善は通常のコミットとして履歴に残る。

ジョブ一覧（初期セット）： draft（種別別の下書き生成。ストーリー漫画のみ内部が2段：場面リスト承認→ネーム生成 §4.0）／ revise（選択範囲への修正指示）／ image（§7）／vocab（§9）／tts-script（§8の原稿整形）。 すべて入出力がスキーマで固定された「工程」であり、自由会話は存在しない。

7画像生成と編集（gpt-image-gen）

画像はすべて Codex の gpt-image-gen で生成する（AGENTS.md 規律7を継承。手描きSVG自作は禁止のまま）。 既存スキル docs/skills/codex_image_generation.md の一貫性ルールを工房ジョブに組み込む。

ルール工房での実装
参照画像を必ず渡すキャラクター登場パネルは characters/*/reference.png を自動添付。manga の characters[] から解決。

7.1 あとからの編集

  • 再生成：スロットの prompt を開き、差分を一言足して再実行（旧画像は履歴として保持、ワンタップで戻せる）。
  • 差し替え：手元のPNG/WebPをアップロード（自動でWebP化・サイズ検査）。
  • 挿入・削除・並べ替え：パネル／ブロック単位の操作（§4.2・§5）。

8音声生成（Gemini Live TTS）

原稿（台本）は Codex工房が作り、音声は Gemini Live のプリセットボイスで合成する。 既存スキル generating-gemini-live-audio（話者ごとの声提案・行単位WAV・結合）のロジックを bridge の tts ジョブとして移植する。

8.1 フロー

  1. meeting（または manga の朗読）の台本を確認 → 「音声をつくる」
  2. 声えらび：話者ごとにボイスカタログ（名前・特徴・性別）から選択。 サンプル試聴ボタンつき（固定の短文で各ボイスを一度だけ合成しキャッシュ）。
  3. bridge が行単位で合成 → 結合 → Supabase Storage にアップロード
  4. audioUrl と各行の開始秒 at（行WAVの長さから自動計算）をコンテンツに書き戻す → 字幕が音声に自動追従（既存の meeting スキーマの at がそのまま生きる）
  5. プレビューで通し試聴 → 気になる行だけ再合成（行単位なので部分やり直しが安い）
キーの整理：音声合成に使うのは先生のGeminiキー（ローカル .env.studio）。 学習者がLive対話に使うBYOKキー（端末保存）とは別物で、混ざらない。

接続方針 — 既存の進捗保存層をそのまま生かす

  • アプリは既に src/lib/progress/store.ts（差し替え可能な抽象）越しに読み書きしている。 ここに Supabase バックエンドを足すだけで、画面側のコードは変えない。 保存する形も TypeScript 型（TestResult / GameScore / WordMastery）と上表の列を1対1にする。
  • ログイン中＝DB直書き（楽観的更新）。未ログイン＝localStorage のみ（ゲスト練習）。 初回ログイン時に端末の記録を一括アップロードして取り込む（bests は max、回数は加算、attempt は再採番せず端末分を後ろに積む）。
  • RLS：学習者は自分の行のみ読み書き。追記型テーブルは UPDATE/DELETE を許可しない （「初回のみ正式」をアプリ規約でなくDB権限で守る）。profiles.is_admin は全行 SELECT 可。
  • 先生ダッシュボードは集計ビューで提供：v_stage_completion（ステージ別進捗）・ v_weak_words（word_mastery のクラス集計）・v_official_scores（attempt=1 の成績一覧）。 §9 の単語抽出が作った新ステージの効果測定（導入前後の missed 率）もこのビューで見る。

11.3 学習データ②明細層 — 「どんな対話をして、どこで間違えたか」

集計層は「どれくらいできたか」しか答えられない。指導に使うのは 「実際になにを打ち、なにを選び、なにを話したか」なので、 1回の取り組みを activity_sessions でくくり、その下に明細を全部追記する。 明細はすべて追記型（UPDATE/DELETE なし）で、UIの状態管理には使わない——記録専用。

テーブル主な列これで分かること
activity_sessions id, content_id, kind, mode(solo|team), team_id?, login_user_id, started_at, ended_at 1回の取り組み（アーケード1プレイ・会議1回・Live対話1回）の入れ物。以下の明細はすべてこの id にぶら下がる
word_attempts session_id, actor_user_id, stage_id, word_id, phase(reading|meaning), result(correct|miss|timeout), input_text, chosen, expected, combo_after, response_ms, occurred_at アーケードの1問ごとの実際。読みを「じゅうよ」と打った・Websiteを選んだ・時間切ればかり＝速度が合っていない、まで見える
quiz_attempts session_id, actor_user_id, quizset_id, question_id, qtype, result(correct|wrong|partial), answer(jsonb), occurred_at 問題エンジンの1問ごとの答えの中身（選んだ選択肢・入力文・穴埋めの並び・emotion の気持ち／言い方の2段階それぞれ）

プライバシーの取り決め： ①明細（特に live_turns）を読めるのは本人と先生（is_admin）だけ（RLS）。 ②学習者には「対話は文字で記録され、先生が見る」ことを開始画面に明示する。 ③音声データそのものは保存しない（残るのはテキストのみ）。 ④保持期間は年度単位とし、年度末に前年度分をアーカイブ／削除する運用にする（§13 未決 #6）。

11.4 チーム編成と、共有PCでの「だれの記録か」

ペアワーク教材（報告・相談）や教室運用では1台のPCを複数人で使う。 ログインが1アカウントでも、明細行の actor_user_id に「実際にやった人」を入れることで、 共有PCでも個人別の間違い・発話量・参加の偏りを集計できるようにする。

テーブル主な列備考

  2. 画面上部にメンバーチップが常駐し、光っている人＝いまの回答者。 明細行の actor_user_id はこのチップの値で埋まる
  3. 交代はワンタップ。さらに既定でローテーション——アーケードは1問ごと、 Live対話は発話ごとに「つぎは ソピアさんの ばん！」と次の人を光らせる （タップし忘れ対策であり、同時に参加の偏りを防ぐ授業設計でもある。手動変更はいつでも可）
