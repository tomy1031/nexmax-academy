# リニューアル設計方針 — エンジン＋データ分離、DB/認証、検収パイプライン、移行手順

**作成日**: 2026-07-15
**前提文書**: `01_理解設計ガイド.md`（設計原則）、`02_拡張カリキュラム設計書.md`（コンテンツ計画）
**この文書の目的**: 現行の静的HTMLアプリをリニューアルし、**DB（進捗・点数管理）と認証を持つ新アプリを新規開発する**にあたっての、アーキテクチャ原則・データ設計要件・検収パイプライン・エージェント/スキル構成・移行手順を定める。

---

## 0. リニューアルの基本方針

1. **思想は全部持っていく、実装は選んで持っていく。** 現行アプリの価値は理解設計（01参照）にあり、HTMLにはない。新アプリは原則を**エンジンに焼き込む**ことで、コンテンツ作者（人間・AI）が原則を忘れても壊れない構造にする。
2. **旧アプリは移行完了まで現役の授業教材として残す。** 新アプリはストラングラー方式（外側から包んで少しずつ置換）で立ち上げ、ビッグバン切替はしない。
3. **検収基盤（lint・CI・語彙計測）をコンテンツより先に作る。** 過去の「何度もダメ出しして直す」工程を、新環境では最初から自動化された状態で始める。

## 1. アーキテクチャ原則: エンジン＋データ分離

### 1.1 なぜ分離するか

現行アプリは「教材1本＝手作りHTML1枚」だが、完成度の高い教材ほど既にデータ駆動に向かっている（`hearing/scenarioN.js`、`wordtest/stagedata.js`、`summary/data.js`）。新アプリではこれを第一原則に格上げする:

- **学習エンジン** = 少数の再利用コンポーネント（プレイヤー/ランタイム）
- **コンテンツ** = スキーマに従う構造化データ（AI・人間が量産する対象）

効果: ①新教材の制作＝データ1枚の追加になり、AIへの発注が「スキーマを満たすデータを書け」に単純化する ②検収の主戦場がスキーマ検証（機械化可能）になる ③理解設計の原則がエンジン側で強制される。

### 1.2 エンジンコンポーネント一覧（移植元マップ）

| コンポーネント | 現行の移植元 | 焼き込む原則（01の番号） |
|---|---|---|
| Live対話プレイヤー | `hearing/hearing.js`（トグルVAD・字幕・速度・判定3層・劣化運転） | P5, P8, P10, P12 |
| 判定ボード（？？？フリップ）＋マナーバッジ | 同上 | P2, P8 |
| 穴埋めエンジン（Drag/Type切替・表記ゆれ正規化） | `app.js` の checkQuiz/normalizeText/initializeDragAndDrop | P6, P11 |
| 隠し原稿リベール | `listening/soudan/index.html` | P2, P6 |
| キーワード発見スコアリング | `listening/renraku/index.html` | P2, P6 |
| 消去法ボード | `sitsumon/practice/shitsumon.js` Lv0 | P2 |
| メッセージ組み立て（Slack/メール/PRコメント） | `lecture/renraku/slack.html` | P6 |
| 感情2段階問題・仕分け・並べ替え | `summary/data.js` の問題タイプ群 | P7 |
| 報酬演出（フリップ・紙吹雪・星・スタンプ） | 各所 | P2, P8 |

| **ルビレンダラ** | `waterfall_quest` の `{漢字|よみ}` パーサを標準化 | P10 |

| 語彙ポップアップ（n4-word） | `app.js` vocabularyData → DB管理に昇格 | P10 |

### 1.3 「原則の焼き込み」の具体例（実装規約）

守らせるルールは、**守らなくても壊れない構造**に変換できるなら必ずそうする:

1. **フィードバック表示コンポーネントは型付きメッセージしか受けない。** `type: "encourage" | "retry" | "next_action" | "praise"` のenumで、自由文字列の「不正解です」を書く場所自体をなくす。文言はエンジン側の辞書（01のP8語彙規律で検収済み）から出す。
2. **ルビは作者が書かない。** コンテンツは常にプレーンテキスト＋読み辞書で持ち、表示時にエンジンが最長一致でルビを合成する（`shitsumon_data.js` の furigana 方式を標準化）。→「表示用ルビHTMLと判定用プレーンの二重管理」（過去の頻出事故）が構造的に消える。
3. **表記ゆれ正規化は共有ユーティリティ1つ**（NFKC・かなカナ変換・全半角）。判定を書く場所ごとに再実装させない。
4. **選択式UIは「読解確認」コンテキストでのみ使用可**をスキーマで表現する（`quiz` は research 節にのみ存在でき、`production` 節には自由入力/音声型しか置けない）。
5. **ペルソナ10か条・癖スロット**はスキーマのフィールド（`persona.rules[5] = quirk`）として構造化し、自由文で崩れないようにする。

### 1.4 コンテンツスキーマ

01の§6（シナリオ/AI応答/単語ステージ）を出発点に、zod（TypeScript）でスキーマを定義し、**スキーマがそのまま検収の契約**になる。スキーマ変更はマイグレーションスクリプトとセットでのみ許可（後述のスキル `/schema-change`）。

## 2. 技術選定（基準と推奨）

**決定は着手時に行う。ここでは判断基準と既定案のみ定める。**

判断基準: ①教師1〜2名で運用できる（インフラ専任なし）②月額コストが小さい ③認証・DB・行レベル権限が既製で手に入る ④Geminiプロキシ用のサーバ関数が書ける ⑤現チームのスキル（JavaScript）で書ける ⑥静的資産（画像・音声）が多い。

**既定案**: **Next.js（App Router）＋ Supabase（Auth + Postgres + RLS + Storage）**、ホスティングは Netlify または Vercel。
- Supabase: 学生/教師のロールをRLSで表現でき、GAS＋スプレッドシートの代替（教師はSupabaseのテーブルビューでも当座は運用可能）。
- 代替案: Firebase（Auth + Firestore）。教材内でも扱っており馴染みがあるが、集計クエリ（つまずき分析）はPostgresの方が書きやすい。**テレメトリ分析を重視するならSupabase**。
- Gemini呼び出しはすべてサーバ関数経由。キーは単一の共有サーバーキーではなく、**生徒・教師が各自で発行した自分のAPIキーを設定画面から登録する（BYOK）**。登録したキーはクライアントに露出させずDBに保存し、サーバ関数が本人のキーとしてのみ使用する（呼び出しログはここで実装）。**フロントのソースコードにAPIキーをハードコードする旧方式は完全廃止**（画面からの登録UI自体は正規の導線として維持）。

## 3. DB・認証の設計要件（理解設計からの導出）

### 3.1 原則→データモデル要件の対応表

| 理解設計の原則 | DB/認証要件 |
|---|---|
| テスト評価とゲームスコアの分離（P11） | `test_results`（教師が見る成績）と `game_scores`（星・コンボ・ランク）を別テーブルに。学生画面に test_results の失敗履歴を出さない |
| 失敗を罰しない（P8） | `attempts` は全試行を記録するが、学生UIには最高記録と肯定進捗のみ表示。教師UIには試行回数・つまずきを表示 |
| 教師ペーシング（P13） | `class_unlocks`（クラス×ユニットの解錠フラグ）。教師ダッシュボードから開放。パスワード演出は残してよいが、真のゲートはサーバ側 |
| 成果物到達（P13・02のM12） | `artifacts`（連絡文・要件定義書・バグ票…の成果物本文＋種類＋作成日）。1年分が自動でポートフォリオ化し、面談・就活資料になる |
| 学習の証拠（P13） | `events`（xAPI風: actor / verb / object / result / timestamp）。画面表示・再生・入力・正誤・ヒント使用・離脱・再挑戦をすべて記録 |
| 中断再開（現localStorage） | `progress`（ユニット内の位置・状態JSON）。端末をまたいで再開可能に |
| 語彙支援（P10） | `vocabulary`（語・読み・英語・級）と `unit_vocabulary`（課との対応）。現 `vocabularyData` 280語を移入し、DATA DIVEステージとポップアップ辞書の単一ソースにする |

### 3.2 エンティティ概要

```
users(id, role: student|teacher|admin, name, class_id, ...)
classes(id, name, teacher_id)
units(id, slug, title, type: lecture|listening|game|live|wordstage, schema_version)
contents(id, unit_id, version, data: jsonb)          -- スキーマ準拠のコンテンツ本体
class_unlocks(class_id, unit_id, unlocked_at, by)
progress(user_id, unit_id, state: jsonb, updated_at)
attempts(id, user_id, unit_id, started_at, finished_at, summary: jsonb)
test_results(id, user_id, unit_id, score, passed, at)
game_scores(id, user_id, unit_id, stars, best, plays)
artifacts(id, user_id, unit_id, kind, body, created_at)
events(id, user_id, unit_id, verb, object, result: jsonb, at)
vocabulary(id, term, reading, meaning_en, jlpt_level)
unit_vocabulary(unit_id, vocabulary_id)
```

### 3.3 認証

- 学生は学校管理アカウント（メール不要のID+パスコード方式も検討。年少者・メール未所持に配慮）。
- ロールは student / teacher / admin の3種。RLSで「学生は自分のデータのみ」「教師は自クラスのみ」。
- 旧GASスプレッドシートの過去成績は、必要なら一括インポートスクリプトで `test_results` に取り込む（新学期から新規スタートでよければ省略可）。

## 4. 検収パイプライン（4段構え）

「N4ペルソナに感想を聞く」方式は廃止し、**計測→証拠→試遊→実測**の4段に再編する。

### 第1段: 機械計測（LLM不使用・CI必須）

`scripts/lint_content.mjs`（pre-commit＋CIで実行）:
- スキーマ検証（zod）: r1〜r10網羅・keywords3語以上・doc全reqId配置・quizがresearch節のみ
- 禁止語 grep: 「不正解」「間違いです」「ダメ」等（P8語彙規律）
- ルビ健全性: プレーン系フィールドへのHTML混入、読み辞書の未登録語
- リンク・ファイル名の大文字小文字・`node --check` / `tsc`

`scripts/measure_readability.mjs`（**語彙計測 — 旧ペルソナ検収の代替の半分**）:
- JLPT級別語彙リスト（N5/N4/N3）と教材全テキストを突き合わせ、画面ごとに出力:
  - N4超語彙の出現率（%）と一覧（ポップアップ辞書登録済みかを併記）
  - 30字超の文の一覧、1画面あたりの新出語数
- しきい値（例: 未知語率10%超・辞書未登録3語以上で警告）をCIでレポート化。「難しいと思います」という感想を数値に置き換える。

### 第2段: 証拠必須・分割LLMレビュー（複数エージェント併用）

- **ルーブリックは `docs/design/01` の品質チェックリストを唯一のソース**とし、各項目を「**該当箇所を引用せよ。引用できなければ違反**」という反証可能な質問形式に書き換えた `docs/design/review_rubric.md` を作る。
- **1エージェント1原則**に分割して並行実行（13原則×小さなチェック。安価なモデルで可）。1体に13原則を全部見せると注意が希釈される。
- **ツール間の分業**（同じ質問を複数ツールに投げない。視点を割り当てる）:
  - **Claude** — 理解設計・言語設計・シナリオ品質（本文書群の思想の検収）
  - **Codex** — コード品質・認証/DB/RLSのセキュリティ・E2Eの穴（新規実装の敵対役）
  - **Gemini** — **Liveペルソナの実機挙動検証**: 本番ランタイムはGeminiなので、「10か条が実際のGemini上で守られるか」（聞かれる前に喋らないか・N4語彙か・癖の頻度）をGemini自身に大量試行させて統計を取る
- 全員に「違反を見つけたら勝ち」のフレーミング。判定は合議でなく**指摘の和集合**。
- 配置: ルーブリックを指す薄いアダプタのみ各ツールに置く — `CLAUDE.md` / `AGENTS.md`（Codex）/ `.gemini/rules.md`。**3箇所に別内容を書かない。**

### 第3段: Playwright試遊（ソースではなく実画面）

- エージェントがPlaywrightで**実際に画面を操作して通しプレイ**する。シナリオJSの読解は学生の体験ではない。
- ペルソナは3体走らせる: **N5で苦しい子／N4中位／退屈しているN3挑戦者**。理解設計はレベル差の吸収が目的なので、「N3が飽きた」も「N5が溺れた」と同格の違反として報告させる。
- 感想ではなく**理解度プローブ**で測る: 各画面で「今あなたは何をすべきか」「このボタンを押すと何が起きるか」に教材内の情報だけで答えさせ、答えられなければ導線設計の失敗と判定。
- 併せて通常のE2E（認証・権限・進捗保存・オフライン系の回帰）もこの段でCI化。

### 第4段: 実学生テレメトリ（最終判定者）

- `events` テーブルから**つまずきレポート**を定期生成: 画面別の離脱率・連続失敗・長考・ヒント多用・再挑戦率。
- しきい値超の画面を自動で改善候補に挙げ、教材改訂ループの入力にする。**模擬ペルソナは「リリース前の粗取り」、実学生データが「本検収」**という役割分担に固定する。

## 5. エージェント/スキル構成（新リポジトリ）

4層分離（知識＝docs/design、手順＝スキル、判断＝エージェント、機械検査＝スクリプト）は変えない。新規開発に伴う追加は次のとおり。

**スキル（7本）**
1. `/kyozai-shinki` — 新教材の企画（レシピStep 0〜9を対話で。設計シート承認までコードを書かない）
2. `/scenario-tsuika` — Liveシナリオのデータ生成（スキーマ＋10か条＋秘匿分離）
3. `/word-stage` — DATA DIVEステージ生成（語彙リスト→stagedata）
4. `/kenshu` — 検収パイプライン第1〜3段の起動と結果集約
5. `/gazou-shiyou` — 画像仕様書と生成プロンプト
6. `/schema-change` — **新規**: スキーマ変更＋マイグレーション＋既存コンテンツ影響チェックをセットで
7. `/engine-component` — **新規**: 新メカニクスをエンジンに追加する際の規約適用（焼き込み原則の遵守）

**エージェント**
- `rubric-checker`×13（原則別・証拠必須） / `playwright-player`×3（レベル別ペルソナ試遊） / `persona-verifier`（Gemini側でLiveペルソナ統計検証）
- 旧「n4-student（感想型）」は廃止。

## 6. 移行手順（フェーズ0〜4）

### 移植・再実装・据え置きの区分

| 区分 | 対象 | 方法 |
|---|---|---|
| **データ移植（ほぼ無変更）** | hearing scenario1〜5 / wordtest stagedata全10 / summary(まなびの島) data.js / vocabularyData 280語 | 新スキーマへ変換スクリプトで一括変換（構造が近いので機械変換＋検収） |
| **エンジン化して再実装** | Live対話・穴埋め・リベール・キーワード発見・消去法・メッセージ組み立て・報酬演出 | §1.2の移植元から抽出し、コンポーネント化 |
| **当面そのまま包む** | 手作りHTMLレクチャー（報連相講義等）・waterfall_quest・ITデュエルモンスターズ | 新シェル内にそのまま表示（iframe/静的配信）し、テレメトリ薄層（開始/完了イベントのみ）を挟む。置換は後回しでよい |
| **廃止** | フロントのAPIキー入力・GAS送信・localStorage進捗（新規分） | サーバプロキシ・DBに置換。旧アプリでは移行完了まで存続 |

### フェーズ0: 立ち上げ（新リポジトリ）

1. 新リポジトリ作成、技術選定の確定（§2の基準で決定）
2. **知識層の移植を最初に行う**: `docs/design/01〜03` をコピーし、薄い `CLAUDE.md` / `AGENTS.md` / `.gemini/rules.md`（すべてルーブリックとガイドへのポインタのみ）を配置
3. **検収基盤をコンテンツより先に構築**: `lint_content.mjs`・`measure_readability.mjs`（JLPT語彙リスト同梱）・CI（GitHub Actions: lint→スキーマ→単体→E2E）・pre-commitフック
4. スキーマ定義（zod）: シナリオ／単語ステージ／クイズ／ペルソナ。§1.4

### フェーズ1: 骨格（認証・DB・プロキシ）

5. Supabase等で認証（student/teacher/admin＋RLS）と §3.2 のテーブル群
6. Geminiサーバプロキシ（ユーザー登録キーの設定画面・保管・呼び出しログ）
7. 教師ダッシュボード最小版（クラス作成・ユニット解錠・成績閲覧）——**GASスプレッドシート運用の置換に足る最小機能**

### フェーズ2: エンジン第1弾＋パイロット1本

8. 最重要3コンポーネントを移植: **Live対話プレイヤー・穴埋めエンジン・報酬演出**
9. パイロット教材1本を選ぶ——推奨は **hearing第1話（ベーカリー）**。理由: データ駆動が最も進んでおり、変換の型が作れる／Live・判定・報酬の全部品を通る
10. パイロットを検収パイプライン4段のうち1〜3段に通し、**実クラスで旧版と並行使用**して4段目（テレメトリ）の初データを取る。ここで移行の型（変換スクリプト・検収・授業運用）を固める

### フェーズ3: 一括移行と並行運用

11. データ駆動コンテンツを一括変換（hearing残り4話→wordtest10ステージ→まなびの島）
12. リスニング教材をエンジン化パターン（リベール・キーワード発見・穴埋め）で順次再実装
13. 手作りHTML教材は「そのまま包む」区分で新シェルに収容（授業導線を新アプリに一本化）
14. 並行運用ルール: 新学期のクラスから新アプリ、既存クラスは学期末まで旧アプリ。**成績の二重管理期間を1学期以内に限定**
15. 切替条件（すべて満たしたら旧アプリを参照専用化）: 教師ダッシュボードでGAS運用を完全代替／パイロット2単元でつまずきレポートが機能／E2Eグリーンが2週間継続

### フェーズ4: 拡張カリキュラム開始

16. `02_拡張カリキュラム設計書.md` のフェーズ1（Live共通基盤→M2朝会→M7障害対応→DATA DIVEステージ12・17）を**新エンジン上で**開始。旧アプリには追加実装しない

### 移行しないもの・注意

- 旧リポジトリは**教材の原本・設計資料庫**として凍結保存（削除しない）。画像・音声資産は新Storageへコピー。
- 実在人物由来キャラ画像は、移行時に同意範囲・公開範囲を再確認（`e_learning_material_creation_skill.md` の運用ルール準拠）。
- localStorageの学習途中データは移行しない（新学期切替で自然消滅させる）。過去成績はGASシートからのインポートで必要分のみ。

## 8. まとめ

リニューアルの核は「**原則をエンジンに焼き込み、検収を計測に変える**」こと。コンテンツはデータになり、AI発注は単純になり、過去に人力で繰り返したダメ出しは lint・スキーマ・ルーブリック・テレメトリに固定化される。移行はストラングラー方式で、パイロット1本（ベーカリー編）で型を作ってから一括変換する。旧アプリは学期をまたぐ並行運用の後、原本として凍結する。
