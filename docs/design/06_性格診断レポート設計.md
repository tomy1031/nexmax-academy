# 性格診断レポート設計 — 記録・個別閲覧・傾向ダッシュボード

**作成日**: 2026-07-26
**位置づけ**: 05設計書の性格診断（20問3択）の結果を、教師が「記録として残し・個別に読み・全体の傾向として見る」ための設計。
**読者**: 教師・管理者。**この画面群は学習者向けではないため、ふりがな不要・通常の日本語で書く**（05 §4.4 と同じ規律）。

## 0. なにを解きたいのか

教師の問いは3つある。画面もこの3つに対応させる。

| 教師の問い | 画面 |
|---|---|
| 「この学生はどういう子か」 | 個別レポート `/admin/students/[id]` |
| 「クラス全体はどうなっているか」 | ダッシュボード `/admin` |
| 「誰と誰を組ませるか」 | ダッシュボードのチーム編成セクション |

3つ目が20問に増やした本来の目的（05 §3）。単なる集計で終わらせず、**編成の判断材料まで出す**ことを設計に含める。

## 1. データ設計

### 1.1 二層構造

- `profiles`（既存）: **最新の状態**。`personality_type` / `answers` / `scores`。画面の高速な読み出しはこちら。
- `personality_results`（新規・`supabase/migrations/20260726100000_personality_results.sql`）: **記録台帳**。診断を完了するたびに1行 insert する追記専用。学生がやり直しても過去が消えない。

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| profile_id | uuid FK → profiles(id) cascade | |
| personality_type | text check 4種 | 判定タイプ |
| answers | jsonb | 20要素 `"yes"｜"neutral"｜"no"` |
| scores | jsonb | 4軸 各0〜10 |
| created_at | timestamptz | 受験日時 |

RLS: 本人は自分の行を select / insert。管理者は全行 select / delete。

### 1.2 書き込み点

`welcome-wizard` の `finish()` で `upsertOwnProfile()` の直後に `insertPersonalityResult()` を呼ぶ。
**台帳への insert が失敗しても学習は止めない**（profiles が保存できていれば `/map` へ進む。台帳はあくまで記録）。

## 2. スコアの読み方（画面に出す定義）

- 回答の配点: はい=2 / どちらでもない=1 / いいえ=0
- 各軸5問なので **軸スコアは0〜10**。10に近いほどその傾向が強い
- タイプ = 最大スコアの軸（同点は heart → challenge → idea → leader の順）
- **「スコアが低い＝劣っている」ではない**。画面の文言は優劣でなく傾向として書く（例: ×「リーダー適性が低い」 ○「計画より先に動くタイプ」）

## 3. 画面 A — ダッシュボード `/admin`

上から順に。すべて管理者のみ（`is_admin`）。

### 3.1 KPIタイル（4枚・横並び）

`回答ずみ` / `未回答` / `登録ユーザー数` / `直近7日の回答`。数字が主役（hero number）で、ラベルは小さく下に。グラフにしない。

### 3.2 タイプ分布（横棒・4本）

- 件数の多い順。バーの右に直接ラベル「リーダー 12人（30%）」
- 色は §5 のカテゴリ配色。**凡例＋直接ラベルの両方**を出す（色だけで識別させない）

### 3.3 軸スコアの平均（横棒・4本・0〜10固定軸）

クラス全体がどの軸に寄っているかを見る。各バーに平均値を直接表示。
0〜10の軸を固定することで「満点10のうちどこか」が読める（データ最大値でスケールしない）。

### 3.4 設問別の回答分布（20行・積み上げ横棒）

各設問について はい / どちらでもない / いいえ の割合を積み上げる。**これが一番の情報源**——
「全員がいいえの設問」「意見が割れる設問」が一目でわかる。

- 行ラベル: `Q01` ＋ 設問文（やさしい日本語版・省略しない）
- 並び順は設問番号順（軸ごとにグループ化してもよいが、番号順を既定にする）
- 各セグメントに割合を直接表示（狭くて入らないときは省略し、ホバーで出す）

### 3.5 性別 × タイプ（クロス集計表）

4タイプ × 男性/女性 の人数表。数字が少ないので図にせず表で出す。

### 3.6 チーム編成の参考

- 入力: 「1チームの人数」（既定4・2〜6で選択）
- 出力: 回答ずみの学生を**タイプがなるべく散るように**割り当てたチーム案。
  アルゴリズムは単純でよい: タイプごとの列を作り、各チームに1人ずつラウンドロビンで配る。
  余りは人数の少ないチームから順に足す
- 各チームカードに、メンバー名＋タイプチップ＋チームの軸スコア合計（4軸のバランスが見える）
- 「これは参考です。最終的な組み合わせは先生が決めてください。」の一文を必ず添える

### 3.7 データ出力

`CSVをダウンロード` ボタン。列: メール, なまえ, 性別, タイプ, leader, idea, heart, challenge, Q01〜Q20, 受験日時。
UTF-8 BOM付き（Excelで文字化けさせない）。

## 4. 画面 B — 個別レポート `/admin/students/[id]`

- ヘッダ: なまえ・メール・性別・タイプ（キャラ画像つき）・受験日時
- 軸スコア: 4本の横棒（0〜10固定）＋ 最大軸のハイライト
- 20問の回答一覧: 設問文（やさしい日本語）・軸・回答（アイコン＋文字）・得点。軸ごとに色帯を付ける
- 受験履歴: `personality_results` を新しい順に並べ、2回以上あれば**前回との差分**（タイプが変わった／各軸の増減）を表示
- 「← 一覧へ戻る」

## 5. 図表の規律（配色・形）

**配色は検証済みのものを使う。目分量で変えない**（`dataviz` スキルの validate_palette.js で全ペア検証済み・2026-07-26）。

| 用途 | 色 |
|---|---|
| leader | `#0272ae` |
| idea | `#1f7a4d` |
| heart | `#f27bb0` |
| challenge | `#d99000` |
| はい | `#1f7a4d` |
| どちらでもない | `#9db0c2` |
| いいえ | `#c9552f` |

- 検証結果: 明度帯・彩度・色覚多様性の分離（全ペア最悪ΔE 12.3）・通常視力の分離すべて PASS。
  コントラストは heart / challenge が3:1未満のため、**直接ラベルと表ビューを必ず併設**すること（これが免除条件）
- バーは角丸4pxを値側の端だけに付け、基線に接地させる。積み上げの区切りは2pxの背景色の隙間
- 目盛り・グリッドは控えめ（`--color-hairline`）。数値・ラベルの文字色は系列色にせず ink 系トークンを使う
- 2系列以上には必ず凡例。加えて4系列以下は直接ラベルも出す（色だけに頼らない）
- 各図に「表で見る」トグルを置き、同じ数字を `<table>` で読めるようにする
- バーはホバーで内訳ツールチップ（設問別は「はい n人 / どちらでもない n人 / いいえ n人」）
- 外部グラフライブラリは入れない。div/CSS と必要なら軽量なインラインSVGで組む

## 6. 空・少数データのふるまい

- 回答者0人: 各セクションに「まだ回答がありません。学生が診断を終えると、ここに傾向が出ます。」
- 回答者1〜2人: 割合(%)は誤解を生むので**件数のみ**を表示する
- チーム編成はチーム数が組めない人数（1チーム分未満）のとき、その旨を出して案を作らない

- 集計ロジックは**必ず純関数に切り出して** `tests/` で検証する（画面と混ぜない）。
  最低限: タイプ分布・軸平均・設問別集計・チーム編成の4つに、空配列と1人のケースを含める
- 管理画面の共通ヘッダに「ダッシュボード / ユーザー / CSV」のナビを置く
