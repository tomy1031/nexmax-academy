## 0. なにを解きたいのか

教師の問いは3つある。画面もこの3つに対応させる。

| 教師の問い | 画面 |
|---|---|
| 「この学生はどういう子か」 | 個別レポート `/admin/students/[id]` |
| 「クラス全体はどうなっているか」 | ダッシュボード `/admin` |
| 「誰と誰を組ませるか」 | ダッシュボードのチーム編成セクション |

3つ目が20問に増やした本来の目的（05 §3）。単なる集計で終わらせず、**編成の判断材料まで出す**ことを設計に含める。

## 1. データ設計

### 1.1 二層構造

- `profiles`（既存）: **最新の状態**。`personality_type` / `answers` / `scores`。画面の高速な読み出しはこちら。
- `personality_results`（新規・`supabase/migrations/20260726100000_personality_results.sql`）: **記録台帳**。診断を完了するたびに1行 insert する追記専用。学生がやり直しても過去が消えない。

> **（v3で変更）** この表の値域は 07 §8 に移管した。現在の正は 07 §8 と実装
> `supabase/migrations/20260727120000_personality_v3.sql`・`src/lib/profile-db.ts` を参照。

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| profile_id | uuid FK → profiles(id) cascade | |
| personality_type | text check 16コード | 判定タイプ（`ISTJ` など） |
| answers | jsonb | 20要素 `"a"｜"b"` |
| scores | jsonb | `ei`／`sn`／`tf`／`jp` 各0〜5（左の極の点数） |
| personality_version | integer | 診断方式の版（v3 は `3`） |
| created_at | timestamptz | 受験日時 |

RLS: 本人は自分の行を select / insert。管理者は全行 select / delete。

### 1.2 書き込み点

`welcome-wizard` の `finish()` で `upsertOwnProfile()` の直後に `insertPersonalityResult()` を呼ぶ。
**台帳への insert が失敗しても学習は止めない**（profiles が保存できていれば `/map` へ進む。台帳はあくまで記録）。

## 2. スコアの読み方（画面に出す定義）

> **（v3で変更）** この節の配点・値域・タイプ判定は 07 §4 に移管した。現在の正は 07 §4 と実装
> `src/content/personality.ts`（`calculatePersonalityScores` / `pickPersonalityCode`）を参照。
> 最終行の「スコアが低い＝劣っているではない」の規律だけは本書が正典として生きている（07 §1.1・§6.4 が参照）。

- 回答は Ⓐ/Ⓑ の2択。選ばれた側の**極に1点**（「どちらでもない」は無い）
- 各軸5問なので **軸の合計は必ず5点**（E+I=5 など）。保存値は左の極（E/S/T/J）側の0〜5で、**双極**（中央2.5）として読む
- タイプ = 4軸それぞれ「左の極が3点以上か」で決まる4文字コード。奇数なので同点は構造的に起きず、タイブレークは存在しない
- **「スコアが低い＝劣っている」ではない**。画面の文言は優劣でなく傾向として書く（例: ×「E が弱い」 ○「I が 4」）

## 3. 画面 A — ダッシュボード `/admin`

上から順に。すべて管理者のみ（`is_admin`）。

### 3.1 KPIタイル（4枚・横並び）

`回答ずみ` / `未回答` / `登録ユーザー数` / `直近7日の回答`。数字が主役（hero number）で、ラベルは小さく下に。グラフにしない。

### 3.2 タイプ分布（横棒・4本）

> **（v3で変更）** 集計単位は 07 §7 に移管した。現在は **4家族の横棒＋家族内の16コード内訳**
> （例「まもり組 12人」の中に ISTJ/ISFJ/ESTJ/ESFJ）。実装は `src/lib/personality-stats.ts`・
> `src/components/admin/admin-ui.tsx` を参照。

- 件数の多い順。バーの右に直接ラベル「まもり組 12人（30%）」
- 色は §5 のカテゴリ配色。**凡例＋直接ラベルの両方**を出す（色だけで識別させない）

### 3.3 軸スコアの平均（双極バー・4本・0〜5固定軸）

> **（v3で変更）** 単方向の0〜10棒は 07 §7 で**双極バー（0〜5・中央2.5）**に差し替えた。
> 0〜5の単方向棒は「低い＝弱い」と誤読させるため使わない（07 §6.4）。実装は
> `src/components/admin/admin-ui.tsx` の `BipolarBar`（中央2.5に印を置き、寄っている側へ伸ばす）。

クラス全体がどの軸に寄っているかを見る。各バーに平均値を直接表示。
0〜5の軸を固定することで「中央2.5からどちらの極へ寄っているか」が読める（データ最大値でスケールしない）。
平均だけだと二峰性が隠れる（`[5,0,5,0]` と `[3,2,3,2]` は同じ2.5）ので、両極の人数も添える。

### 3.4 設問別の回答分布（20行・積み上げ横棒）

> **（v3で変更）** 3値（はい／どちらでもない／いいえ）は 07 §7 で **Ⓐ/Ⓑ の2値**になった。
> 色は選択肢でなく**極**に割り当てる（Ⓐ/Ⓑに割り当てると設問間で意味が反転する。
> `src/components/admin/admin-ui.tsx` の `POLE_COLORS`）。

各設問について Ⓐ / Ⓑ の割合を積み上げる。**これが一番の情報源**——
「全員が同じ側の設問」「意見が割れる設問」が一目でわかる。

- 行ラベル: `Q01` ＋ 設問文（やさしい日本語版・省略しない）
- 並び順は設問番号順（軸ごとにグループ化してもよいが、番号順を既定にする）
- 各セグメントに割合を直接表示（狭くて入らないときは省略し、ホバーで出す）

### 3.5 性別 × タイプ（クロス集計表）

> **（v3で変更）** 集計単位は 07 §7 に移管した。**家族単位の 4×2**（16コードでは1マス0〜1人になり読めない）。

4家族 × 男性/女性 の人数表。数字が少ないので図にせず表で出す。

### 3.6 チーム編成の参考

> **（v3で変更）** ラウンドロビン方式は 07 §6（評価関数つきチーム編成 v2）に移管した。現在の正は
> 07 §6 と実装 `src/lib/personality-stats.ts` を参照。ペナルティ関数（J不在・F不在・家族のかたまり・
> 同一コード重複・E:I のずれ）＋貪欲法＋入れ替え改善で、決定的（乱数なし）に組む。

- 入力: 「1チームの人数」（既定4・2〜6で選択）
- 各チームカードに、メンバー（呼び名＋4文字コード＋エンブレム）・家族の内訳・足りない役割の警告チップ（07 §6.4）
- 「これは参考です。最終的な組み合わせは先生が決めてください。」の一文を必ず添える

### 3.7 データ出力

> **（v3で変更）** 列構成は実装 `src/lib/personality-csv.ts`（`buildPersonalityCsv`）を正とする。
> タイプ列は「まじめの ネクマックス」等の呼び名で出し、4文字コードは出さない。

`CSVをダウンロード` ボタン。列: メール, なまえ, 性別, タイプ, 組, 版, ei, sn, tf, jp, Q01〜Q20, 受験日時。
UTF-8 BOM付き（Excelで文字化けさせない）。未診断の行も名簿として出すが、タイプ由来の列は空にする。

## 4. 画面 B — 個別レポート `/admin/students/[id]`

> **（v3で変更）** 軸表示と履歴比較は 07 §7 に移管した。軸スコアは**双極バー**（0〜5・中央2.5・
> `BipolarBar`）で出し、「最大軸のハイライト」はしない（軸ごとに独立した双極で、最大軸という概念が無い）。
> 履歴比較は **`personality_version` が同じ結果同士だけ**行い、版が違う場合は
> 「診断方式が変わったため比較できません」と表示する。

- ヘッダ: なまえ・メール・性別・タイプ（キャラ画像つき）・受験日時
- 軸スコア: 4本の双極バー（0〜5・中央2.5）
- 20問の回答一覧: 設問文（やさしい日本語）・軸・回答（Ⓐ/Ⓑと選んだ極）。軸ごとに色帯を付ける
- 受験履歴: `personality_results` を新しい順に並べ、同じ版が2回以上あれば**前回との差分**（タイプが変わった／各軸の増減）を表示
- 「← 一覧へ戻る」

## 5. 図表の規律（配色・形）

**配色は検証済みのものを使う。目分量で変えない**（`dataviz` スキルの validate_palette.js で全ペア検証済み・2026-07-26）。

> **（v3で変更）** 「はい／どちらでもない／いいえ」の3色は廃止し、設問別分布は**極の2色**を使う
> （`src/components/admin/admin-ui.tsx` の `POLE_COLORS`）。家族4色は `FAMILY_COLORS` として存続。

| 用途 | 色 |
|---|---|
| leader（まもり組） | `#0272ae` |
| idea（かんがえ組） | `#1f7a4d` |
| heart（きもち組） | `#f27bb0` |
| challenge（うごき組） | `#d99000` |
| 左の極（E / S / T / J） | `#0272ae` |
| 右の極（I / N / F / P） | `#d99000` |

- 検証結果: 明度帯・彩度・色覚多様性の分離（全ペア最悪ΔE 12.3）・通常視力の分離すべて PASS。
  コントラストは heart / challenge が3:1未満のため、**直接ラベルと表ビューを必ず併設**すること（これが免除条件）
- バーは角丸4pxを値側の端だけに付け、基線に接地させる。積み上げの区切りは2pxの背景色の隙間
- 目盛り・グリッドは控えめ（`--color-hairline`）。数値・ラベルの文字色は系列色にせず ink 系トークンを使う
- 2系列以上には必ず凡例。加えて4系列以下は直接ラベルも出す（色だけに頼らない）
- 各図に「表で見る」トグルを置き、同じ数字を `<table>` で読めるようにする
- バーはホバーで内訳ツールチップ（設問別は「はい n人 / どちらでもない n人 / いいえ n人」）
- 外部グラフライブラリは入れない。div/CSS と必要なら軽量なインラインSVGで組む

## 6. 空・少数データのふるまい

- 回答者0人: 各セクションに「まだ回答がありません。学生が診断を終えると、ここに傾向が出ます。」
- 回答者1〜2人: 割合(%)は誤解を生むので**件数のみ**を表示する
- チーム編成はチーム数が組めない人数（1チーム分未満）のとき、その旨を出して案を作らない
