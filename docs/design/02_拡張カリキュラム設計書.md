# 拡張カリキュラム設計書 —「ネクストメイク1年目」編

**対象リポジトリ**: `nextmake_onbording`（Japanese IT Pathway プログラム）
**作成日**: 2026-07-15
**前提文書**: `docs/design/01_理解設計ガイド.md`（本書のすべてのモジュールは、同ガイドの13原則・制作レシピ・データ構造テンプレートに従って作る）

**この文書の目的**: 現行教材が未カバーの「日本のIT現場で働くために必要な知識」を洗い出し、**全工程をGemini Live等の直接対話で、日本語アウトプット主体で、飽きずに追体験できる**包括カリキュラムとして設計する。単語・用語は既存の単語ゲーム「DATA DIVE」に**課ごとのステージを追加するだけ**でゲーム化する（ゲーム本体は変更しない）。

## 2. 拡張の設計方針

1. **理解設計ガイドの13原則を全モジュールに適用する**。特に「選択式に逃げない」「不正解を言わない」「日本語アウトプットで終わる」「単語はDATA DIVEへ」。
2. **すべてのモジュールにGemini Live（音声対話）の場面を1つ以上置く**。既存 `hearing.js` の基盤（トグル式マイク・字幕・0.75倍速・フレーズカード・テキスト代替・判定3層・劣化運転）をライブラリ化して使い回す（§6）。
3. **1つの物語で貫く**:「ネクストメイク1年目」。学習者は研修（現行教材）を終えて**開発チームに配属された自分**を演じる。季節が進む＝カリキュラムが進む。
4. **4択の代わりに使う手法は「学習手法パレット」（§4）から選ぶ**。既存アプリで実証済みのメカニクスを新しい題材に転用することを基本とし、新規メカニクスは3つだけ追加する。
5. **アウトプットの定義**: 各モジュールは「声に出す成果物（Live対話）」と「手に残る成果物（日本語の実務文書）」を必ず両方持つ。
6. **語彙は課ごとに8〜12語**を先出しし、同じ語をLive対話で相手に使わせ、DATA DIVEの追加ステージ（§5の各モジュール仕様）で反復する。

## 3. ナラティブ設計 —「ネクストメイク1年目」

### 3.1 物語の骨格

> 研修を終えたあなたは、ネクストメイクの開発チームに配属された。チームは、そら書店の「イベント管理アプリ」（しつもんゲーム最終レベルで要件定義書が完成しているあの案件）を、これから1年かけて開発する。**あなたが研修で聞き出した要件が、本物のプロジェクトになる。**

- 現行教材の到達点（要件定義書の完成）を、そのまま拡張カリキュラムの開始点にする。**学習者が過去に自分で作った成果物が、次の教材の「仕様書」として再登場する**——これが最大のワクワク装置であり、復習装置でもある。
- 季節イベントを織り込む: 4月配属・自己紹介 → 夏の開発とレビュー → 秋の障害と顧客対応 → 冬のリリース → 年度末の評価面談・発表会。日本の会社の1年のリズム自体が学習内容になる。

### 3.2 登場人物（既存キャラの継続＋最小限の追加）

| キャラ | 役割 | 教育機能（癖） |
|---|---|---|
| ヘンディ先輩（既存） | 直属のPM。朝会の司会 | ミッション提示と攻略tip。変えない |
| 藤木さん（既存） | 取締役。評価面談・障害エスカレーション先 | 「結論から」を求める |
| ニャムさん（既存） | 出向エンジニアの同僚。コードは優秀・日本語N4学習中 | ペア相手。学習者が「教える側」になる場面を作る |
| 大空社長（既存・そら書店） | 顧客。進捗報告・デモの相手 | ITは苦手。専門用語を使うと聞き返す |
| **新キャラ①: 桂木さん（QAリーダー・40代女性）** | テスト・バグ票・品質の門番 | 「再現手順がないバグ票は受け取らない」が口癖。厳しいが、良い報告は必ず具体的に褒める |

新キャラは2人まで。それ以外の場面（電話応対・面接官など）は既存キャラの兼任か単発ゲストで賄い、世界を薄めない。

## 4. 学習手法パレット（「飽きさせない」ための道具箱）

**原則: 新モジュールを設計するとき、この表から題材に合う手法を選ぶ。同じ手法を2モジュール連続で主役にしない。**

### 4.1 実証済みメカニクスの転用マップ

| 既存メカニクス（出典） | 新しい使い所 |
|---|---|
| Zoom風Live対話＋要件ボード「？？？」フリップ（hearing） | 朝会・1on1・面接など、聞き出す系すべて。ボードの中身を「報告できた項目」「面接で伝えられた強み」に差し替える |
| 消去法の可視化（しつもんLv0） | **障害の原因切り分け**。「サーバー？DB？ネットワーク？昨日のリリース？」を質問で✕にしていく——デバッグ思考と質問力の合体 |
| Slackクローンの文章組み立て＋ドラフト蓄積（slack.html） | チケットのコメント返信、PRレビューへの返信、リリース告知 |
| 隠し原稿リベール（listening/soudan） | 設計書・議事録の読解。「読めた行から開く」設計書リーディング |
| 感情2段階問題（まなびの島kyokan） | **レビューコメントの意図読み取り**（この指摘は怒っている？助けている？→どう返す？） |
| カードバトルのカウンター＝実務の台詞（IT デュエルモンスターズ） | 顧客交渉・リスケ交渉の「切り返しカード」（納期短縮要求 ⇔ スコープ調整案の提示） |
| 隠しリスク蓄積→後工程で爆発（waterfall_quest） | 見積もりゲーム: バッファを削る選択が後半の障害イベントで爆発する |
| 反省クイズ→復活（waterfall_quest） | 全ゲーム共通の敗者復活として標準搭載 |
| 良い例/悪い例の対比＋受け手の心の声（renraku講義） | 敬語・メール・バグ票の講義パート |
| 議事録完成穴埋め（youken_teigi） | 会議モジュールの変換課題（発展形: 自分が議事録担当としてLive会議を聞きながら書く） |
| 開錠パスワード＝学習内容（aizuchi） | 各モジュールのゲート（例: 障害編の合言葉は「じじつ・えいきょう・みこみ」） |
| 分かち書き漫画14コマ（onepage/manga） | 各モジュールの導入ストーリー。失敗→気づきの定番構成 |
| 修了証・星・島スタンプ（各所） | 1年目カレンダーに「季節スタンプ」が貯まる進捗画面 |

### 4.2 新規メカニクス（3つだけ追加する）

1. **電話モード**（M7・M9で使用）: Live対話から**顔タイルと字幕を消した**バージョン。画面には黒い受話器UIと「もう一度おねがいします」ボタンだけ。字幕は上級でOFF・初級でON。**日本語学習者が最も怖い「声だけの日本語」を、安全に反復できる場**。着信音→深呼吸カウント3秒→応答、の儀式で緊張も演出する。
2. **インボックス・シミュレーション**（M3・M8で使用）: 出社するとSlack・メール・チケットが同時に溜まっている画面。**全部には対応できない量**を渡し、優先順位を付けて上位だけ処理させる。「正解の順番」ではなく「その順にした理由」を後でヘンディ先輩（AI）に日本語で説明するところまでが課題。
3. **分岐マンガ**（M5・M11で使用）: 漫画の途中で選択肢が出て、選んだ行動でコマが分岐する（2分岐×2回程度）。バッドエンドも「叱責」ではなく「気まずい沈黙→翌日リカバリーできる」構成にし、必ず両方の枝を読み比べられる。

## 5. モジュール詳細設計（M1〜M12＋卒業制作）

各モジュールは共通フォーマットで示す。**到達目標／物語／学習フロー（インプット→変換→産出）／Gemini Live設計／手に残る成果物／DATA DIVE追加ステージ（語彙サンプル）／レベル対応**。

---

### M1. 配属初日 — 自己紹介と「よろしくおねがいします」

- **到達目標**: 配属先チームで、名前・出身・得意技術・意気込みを45秒で自己紹介し、雑談の質問に答えられる。
- **物語**: 4月1日。ヘンディ先輩に連れられてチームに挨拶回り。ニャムさん・桂木さん・森本さんと初対面。
- **学習フロー**:
  - インプット: 導入漫画（緊張のソクさん、自己紹介で好印象を残すニャムさんの対比）＋自己紹介の型（名前→出身→できること→ひとこと）講義。良い例/悪い例（長すぎる経歴読み上げ vs 45秒＋笑顔）。
  - 変換: 自己紹介ビルダー——穴あき型文（「◯◯から来ました。大学では◯◯を勉強しました。◯◯が得意です。」）に自分の情報を入れて完成させる。
  - 産出: **Live挨拶回り**。3人のキャラに順番に自己紹介→各キャラが1つずつ雑談質問を返す（桂木さん「カンボジアの料理で何が好き？」等）。
- **Live設計**: 相手役3ペルソナを順番に切替。判定ボードは「なまえ／しゅっしん／とくい／ひとこと／しつもんに答えた」の5枚フリップ。癖: 森本さんは声が小さい（聞き返し練習）。
- **成果物**: 自己紹介カード1枚（写真＋4項目。以後のモジュールでプロフィールとして再利用）。
- **DATA DIVEステージ11「はいぞく」**: 配属（はいぞく）/ 部署（ぶしょ）/ 出身（しゅっしん）/ 得意（とくい）/ 先輩（せんぱい）/ 同期（どうき）/ 挨拶回り（あいさつまわり）/ 意気込み（いきごみ）。
- **レベル対応**: 初級は型文の穴埋めだけでLive可。上級は型文なし＋雑談2往復。

---

### M2. 朝会 — 毎日の3点セット（やった・やる・こまってる）

- **到達目標**: 朝会で「昨日やったこと・今日やること・困っていること」を60秒で言える。困っていることを隠さず、相談に変換できる。
- **物語**: そら書店アプリの開発開始。毎朝9:30、ヘンディ先輩の朝会。**このモジュールは1回で終わらず、以後の全モジュール冒頭に「今日の朝会」として毎回30秒付く**（スパイラルの新しい核）。
- **学習フロー**:
  - インプット: 朝会の意味（「あなたの遅れは、チームの遅れになる前に共有する」）。悪い例:「順調です」（→3日後に爆発）の漫画。
  - 変換: タスクカードから3点セットを組み立てる（インボックスの簡易版）。「終わりました／進んでいます（あと◯％）／詰まっています」の状態語彙。
  - 産出: **Live朝会**。ヘンディ先輩が「ソクさん、お願いします」と振る→60秒で3点→先輩が1つだけ深掘り質問（「詰まっているのは、どのAPIですか？」）。
- **Live設計**: 判定ボード3枚（きのう／きょう/こまりごと）＋マナーバッジ（時間内・結論から・数字あり）。**隠し評価**: 困りごとを言わずに終えると、翌日のシナリオで小さなトラブルが起こる（隠すコストの体感——waterfall_questの隠しリスクの会話版）。
- **成果物**: 分報テンプレ（Slack用の朝会テキスト版）を自分の言葉で1本。
- **DATA DIVEステージ12「あさかい」**: 朝会（あさかい）/ 進捗（しんちょく）/ 順調（じゅんちょう）/ 遅れ（おくれ）/ 詰まる（つまる）/ 共有（きょうゆう）/ 見込み（みこみ）/ 本日（ほんじつ）/ 昨日（さくじつ）。
- **レベル対応**: 初級は3点の型文ボタンあり。上級は先輩の深掘りが2回になり、数字（％・時間）必須。

### M3. チケットとカンバン — 仕事の受け取り方

- **到達目標**: チケット（タスク票）を読んで、期限・優先度・不明点を確認してから着手できる。ステータスを自分で動かし、完了コメントを書ける。
- **物語**: はじめて自分のチケットが割り当てられる。「本の検索画面のプルダウンを追加」。だが書いてある内容に足りない情報がある。
- **学習フロー**:
  - インプット: カンバン（未着手→作業中→レビュー待ち→完了）の講義。チケットの読み方（件名・詳細・期限・優先度・担当）。
  - 変換: **インボックス・シミュレーション（初出）**——チケット4枚＋Slack2件が同時に来る。優先度と期限で処理順を並べる→その順にした理由を書く。
  - 産出: 不明点をヘンディ先輩にSlackクローンで質問（「『プルダウン』の選択肢は、どこから取得しますか？」）→作業完了後、完了コメント（やったこと・確認方法・残課題）を書く。
- **Live設計**: 軽め。並べた優先順位を**口頭で先輩に説明**し、先輩が1箇所だけ揺さぶる（「こっちを先にした理由は？」）。正解の順番は1つではなく、**理由が筋なら承認される**判定。
- **成果物**: 完了コメント1本（以後の全モジュールで「チケットを閉じる」動作として反復）。
- **DATA DIVEステージ13「タスク」**: 起票（きひょう）/ 担当（たんとう）/ 期限（きげん）/ 優先度（ゆうせんど）/ 着手（ちゃくしゅ)/ 完了（かんりょう）/ 保留（ほりゅう）/ 対応中（たいおうちゅう）。

---### M4. 設計書を読む — 仕様の穴を見つけたら勝ち

- **到達目標**: 画面設計書・テーブル定義を読み、書いていないこと（仕様の穴）を見つけて、確認質問ができる。
- **物語**: そら書店アプリの「イベント予約画面」の設計書が渡される。よく読むと、**満席のときどうするかが書いていない**。
- **学習フロー**:
  - インプット: 設計書の種類（画面設計・テーブル定義・API仕様）を、**隠し原稿リベール**の転用で読む——設計書が伏せ字で、項目名を入力すると開く「設計書発掘リーディング」。
  - 変換: 「書いてあること／書いてないこと」仕分けゲーム（まなびの島のsort型转用）。
  - 産出: **Live設計レビュー会議**。ヘンディ先輩＋ニャムさんの前で、見つけた穴を質問する。「もし満席の場合は、どの画面を出しますか？」
- **Live設計**: 判定ボードは「仕様の穴」5枚（満席時/キャンセル時/同時予約/文字数上限/エラー表示）。設計書（調査素材）には**わざと5つの穴**を仕込む——分散ヒント設計の応用で、穴は設計書に「書いていない」ことでのみ示される。ニャムさんの癖: 気づいた穴を先に1つ言ってしまう（残り4つを競う楽しさ＋同僚と協働する感覚）。
- **成果物**: 確認事項リスト（QAシート）1枚——「質問／想定される答え／決まったこと」の3列。
- **DATA DIVEステージ14「せっけい」**: 設計書（せっけいしょ）/ 画面遷移（がめんせんい）/ 項目（こうもく）/ 必須（ひっす）/ 上限（じょうげん）/ 仕様（しよう）/ 例外（れいがい）/ 満席（まんせき）/ 確認事項（かくにんじこう）。

### M5. コードレビュー — 指摘は攻撃ではない

- **到達目標**: レビューコメントの意図（must/提案/好み）を読み分け、感情的にならずに返信し、直したら再依頼できる。
- **物語**: はじめてのプルリクエストに、桂木さん・ニャムさんから7件のコメントが付く。ソクさんは一瞬へこむ——導入は**分岐マンガ**:「黙って全部直す」を選ぶと誤解したまま手戻りする枝、「意図を質問する」を選ぶと早く終わる枝。両方読み比べる。
- **学習フロー**:
  - インプット: レビュー文化の講義（「コードへの指摘は、あなたへの指摘ではない」）。コメントの温度の読み方——**感情2段階問題の転用**:「このコメントを書いた先輩の気持ちは？（心配/提案/急ぎ/好み）」→「どう返す？」。
  - 変換: GitHub風PR画面（Slackクローンの転用）で、7件のコメントに返信を組み立てる。「修正しました」「ここは◯◯という理由でこのままにしたいのですが、いかがでしょうか」「勉強になります。直します」の使い分け。
  - 産出: **Liveレビュー議論**。1件だけ口頭で議論になる——桂木さんの指摘に対して、自分の実装理由を説明し、着地点（今回は直す／次のチケットにする）を合意する。
- **Live設計**: 判定は「理由を説明した／相手の案を確認した／着地を合意した」の3枚。桂木さんの癖: 良い返信には「その返し方、いいですね」と**返信の仕方自体を褒める**。
- **成果物**: レビュー返信集（自分の7返信）＋「直しました」再依頼コメント1本。
- **DATA DIVEステージ15「レビュー」**: 指摘（してき）/ 修正（しゅうせい）/ 反映（はんえい）/ 意図（いと）/ 提案（ていあん）/ 確認（かくにん）/ 承認（しょうにん）/ 差分（さぶん）/ 再依頼（さいいらい）。

### M6. テストとバグ票 — 「再現手順がないバグ票は受け取らない」

- **到達目標**: バグを発見したら、再現手順・期待値・実際値・環境を揃えたバグ票を書き、口頭でも30秒で報告できる。
- **物語**: テスト週間。桂木さんのQAチームに合流。お手本のバグ票と「受け取ってもらえないバグ票」を見る。
- **学習フロー**:
  - インプット: 良い例/悪い例の対比（「なんか変です」vs「手順1→2→3で、期待値Aのところ実際はBになります」）。悪い例には桂木さんの心の声（「どの画面？いつ？私は何をすればいいの？」）。
  - 変換: **バグ再現ハント（ミニゲーム）**——わざと壊してあるそら書店アプリのモック画面を実際に操作し、バグを再現させる。操作ログが自動記録され、それを削って「最短の再現手順」に編集する（**手順の最小化**という実務スキル）。
  - 産出: バグ票を書いてから、**Liveで桂木さんに口頭報告**。桂木さんは票に穴があると「環境は？」「毎回ですか？ときどきですか？」と突っ込む。
- **Live設計**: 判定ボード5枚（手順/期待値/実際値/環境/頻度）。全部揃うと「これは良いバグ票です。すぐ直せます」と**開発者の時間を守った**ことを褒める。
- **成果物**: バグ票2件（再現手順つき）。

### M7. 障害対応 — 静かな声で、事実・影響・見込み

- **到達目標**: 障害発生時に、事実→影響範囲→復旧見込み→次の連絡時刻、の順で第一報を出し、続報と再発防止まで完走できる。
- **物語**: 金曜16時、そら書店から電話——「予約ページが開かないんです！明日イベントなのに！」。森本さんと二人で対応する。**カリキュラム最大の山場**として演出する（ただし制限時間による減点はしない。時計は「動いている」だけ）。
- **学習フロー**:
  - インプット: 導入漫画（あわてて「たぶん大丈夫です」と言ってしまい、燃える枝／静かな森本さんの「事実だけ言いましょう」の枝）。第一報テンプレの講義（train.html の発展）。
  - 変換: **原因切り分けボード（消去法可視化の転用）**——「サーバー？DB？昨日のリリース？外部サービス？」を、森本さんへの質問と管理画面の確認で✕にしていく。デバッグ思考×質問力。
  - 産出①: **電話モード（新メカニクス初出）**で大空社長に第一報。「現在、予約ページが開かない状態です。原因を調査しています。30分後にもう一度ご連絡します」。顔なし・声だけ。
  - 産出②: 復旧後、Slackクローンで社内向け報告（原因・対応・再発防止）を組み立てる。
- **Live設計**: 電話の判定ボード4枚（事実/影響/見込み/次の連絡）。禁止ワード検出——「たぶん」「すぐ」「大丈夫だと思います」が出たら、advice側で「『すぐ』は曖昧です。時間で言いましょう」。大空社長の癖: 不安で同じ質問を2回する（同じ内容を落ち着いて2回言う練習）。
- **成果物**: 障害報告書1枚（発生時刻/事象/影響/原因/対応/再発防止の6項目）。
- **DATA DIVEステージ17「しょうがい」**: 障害（しょうがい）/ 発生（はっせい）/ 影響範囲（えいきょうはんい）/ 復旧（ふっきゅう）/ 見込み（みこみ）/ 一次報告（いちじほうこく）/ 切り分け（きりわけ）/ 再発防止（さいはつぼうし）/ 続報（ぞくほう）。

### M8. 見積もりとリスケ — 「間に合いません」を価値ある報告に変える

- **到達目標**: 作業を分解して工数を見積もり、遅れが見えた時点で「事実＋選択肢つきのリスケ案」を提案できる。
- **物語**: 新機能「イベントのQRチケット」の見積もり依頼。楽観で答えた見積もりが、途中で遅れ始める。
- **学習フロー**:
  - インプット: 見積もりの講義（分解・バッファ・「わからない」の扱い）。waterfall_quest 第5章の実務版。
  - 変換: **見積もりゲーム（隠しリスク転用）**——タスク分解カードに時間を割り当てる。バッファを削って早い納期を約束すると、後半イベント（仕様の追加・体調不良・環境トラブル）で爆発する。2周目で「バッファの意味」が体感に変わる。
  - 産出: **Liveリスケ交渉**。ヘンディ先輩に「予定より2日遅れます。理由は◯◯です。A案: 期限を2日延ばす。B案: QR読み取りだけ先に出す。どちらがよいでしょうか」——**A案B案の提示**（ITデュエルモンスターズのカウンターカードの実演）。
- **Live設計**: 判定ボード4枚（遅れの事実/理由/A案/B案）。先輩の癖: 謝罪が2回を超えると「謝るより、案をください」と促す（謝罪過多の矯正）。
- **成果物**: 見積もり表（タスク/時間/バッファ）＋リスケ提案文。
- **DATA DIVEステージ18「みつもり」**: 見積もり（みつもり）/ 工数（こうすう）/ 分解（ぶんかい）/ 余裕（よゆう）/ 納期（のうき）/ 前倒し（まえだおし）/ 延期（えんき）/ 代替案（だいたいあん）。

## 6. Gemini Live共通基盤の再利用設計

新モジュールのLive対話は、`hearing.js` から次を**共通ライブラリ（例: `lib/live_core.js`）に切り出して**全モジュールで共有する:

1. WebSocket接続とモデルフォールバック（4段・9秒タイムアウト）、手動VADトグルマイク、16kHz送信/24kHz再生
2. 入出力字幕・声の速さ（0.5/0.75/1.0・localStorage共有）・テキスト入力フォールバック
3. 判定3層（REST JSON判定→ローカルキーワード→**和集合**）と劣化運転（429/5xx時の文言含む）
4. 判定ボード（？？？フリップ）・マナーバッジ・結果画面（星・よかったところ・つぎはこれ）
5. ペルソナ10か条契約（癖は第5条スロット差し替え）・進捗localStorageスキーマ

**新モジュールが書くのはデータファイル1枚**（シナリオ＋ペルソナ＋判定ボード定義＋語彙）——既存の「新シナリオ追加レシピ」の思想を全教材に一般化する。新規UIが必要なのは電話モード（顔タイル非表示＋字幕トグルの変種）とマルチキャラ切替（既存のsetAiTile拡張）のみ。

- **APIキー運用**: 全Live教材は「先生がキーを配布・教材にハードコード禁止・キーなしでも調査/変換フェーズまで遊べる」の既存規律を踏襲する。
- **毎朝会の飽き対策**: M2の朝会は毎回同じだと形骸化する。シナリオ側の「今日の小さな出来事」（ニャムさんが休み・リリース前日・雨で遅延）を10種ローテーションし、判定ボードは変えない。
- **電話モードの心理負荷**: 必ず初級（字幕ON）から。初回は「聞き返しフレーズを使えたら成功」という低いバーで成功体験を作ってから、内容の判定に進む。
- **新キャラの声**: 桂木さん・森本さんのLive音声プリセットと口調（1文の長さ・語尾）を最初に確定し、キャラクターシート（性格/口癖/癖と教育的ねらい）を既存設計書の様式で残す。
- **語彙ステージの検収**: `wrongMeanings` は必ず英語・意味的に紛らわしいもの、`example` はレクチャー本文と同じ文脈——既存指示書の規律をステージ11〜22にも適用する。
- **すべての新規テキスト**は理解設計ガイドの品質チェックリスト（「不正解」禁止・全ルビ・N4語彙・概念ラベル非表示・言語力＝能力の混同禁止）で検収する。

## 9. まとめ

現行教材は「案件が始まるまで」を世界最高水準の丁寧さで教えている。本拡張は、その続き——**配属されてからの365日**——を同じ設計原則で埋める。学習者が研修で自分の手で聞き出した要件定義書が本物のプロジェクトになり、朝会で毎日日本語を話し、レビューで打たれ強くなり、障害の電話に静かな声で出られるようになり、最後に自分の1年をポートフォリオとして日本語で語る。**「日本で働く自分」の解像度が上がり続ける限り、N3への道は「勉強」ではなく「準備」になる。**
