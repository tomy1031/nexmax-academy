# 08. 教師向け 授業サポート表示 設計

性格診断の回答（07 v3）を、教師が授業で使える形に翻訳して管理画面に出す。

**結論から書く。この機能は実行時にAIを呼ばない。生成もしない。**
Claude Code が**一度だけ**「定型文の台帳」を書いてリポジトリに置き、管理画面はそれを生徒のスコアとクラス集計から決定的に組み立てて表示する。

前提として読む: `01_理解設計ガイド.md`（13原則）・`06_性格診断レポート設計.md`・`07_性格タイプ設計_MBTI16.md`

---

## 0. なぜこの形か

当初は「講師がボタンを押すとAIが分析する」形で設計した。3段階の検討で、この形に落ち着いた。記録を残す。同じ検討を繰り返さないため。

### 0.1 アプリから外部AIを呼ばない

| 案 | 落とした理由 |
|---|---|
| CodexAppServer（kotoba-tensei と同じ流儀） | 中核が `spawn("codex", ["app-server"])` の常駐子プロセス＋WSトンネル。`codex app-server --help` の1行目が `[experimental]`、WSに認証が無く（`--ws-auth` はヘルプ自身が "for non-loopback listeners" と書く実験的機能）、**ターンのタイムアウトが実装されていない**（`turn/completed` が来なければ Promise が永久に未解決）。サーバレス関数の上には常駐プロセスを置けないので、動かすには常時起動のVMが別途要る |
| Gemini プロキシ API Route（BYOK） | 技術的には動く。**が、生徒の回答を外部サービスへ送る判断をしない**方針になった |

> **デプロイ先について**: `docs/deploy.md:8` の表で Vercel Hobby は「**検証（本書の主対象）**」であり、同 §2 末尾は「本番を Vercel にするか他ホストにするかは 03 の正式運用の判断に従う。検証環境の選定が本番を縛るものではない」と明記している。**したがって「Vercelだから常駐プロセスが置けない」は本番についての論拠にならない。** CodexAppServer を落とす理由は上表の3点（実験的機能・認証なし・タイムアウト未実装）であり、ホスト選定とは独立している。

#### 0.1.1 将来の拡張経路 — Cloudflare Containers 上の CodexAppServer

「常時起動のVMが別途要る」に対する Cloudflare 側の答えは **Containers**（Worker → Durable Object 経由で任意の Docker イメージを動かす。Workers Paid 月額$5・アイドル時は自動スリープして課金停止・月ぶんの無料使用量つき）である。本番を Cloudflare に移す前提なら、`codex` CLI を焼き込んだコンテナで `codex app-server` を常駐させる構成が成立する。

- **認証なし問題は構造的に消える**: コンテナはインターネットから到達できず、Worker 経由でしか触れない。Worker 側で管理者セッションを検証すれば実質 loopback と同じ閉じ方になる
- **WebSocket は双方向で中継され**、メッセージが流れている間はスリープタイマーが更新される（cloudflare/containers README）
- 費用は月$5固定＋既存の Codex サブスクリプション。**上限のない従量課金が発生しない**ので、Gemini を落とした会計上の理由と衝突しない

残る課題: ①ログイン済み `auth.json` の注入と、自動更新されたトークンの永続化（スリープでディスクが消える）②サブスクリプション認証をサーバから使う規約上のグレー ③ `[experimental]`・タイムアウト未実装は変わらないのでラッパーが要る ④ 生成物は §6 の検査を**取り込みの関門**として必ず通す（生成が復活しても検査の設計はそのまま使える）。

**完全無料の変形 — Tunnel 経由でローカルの codex app-server を使う**: Containers の月$5は「常時起動の場所代」でしかない。その場所を**管理者自身のPC**にすれば $0 になる。Cloudflare Tunnel は無料・使用量制限なし、Zero Trust（Access）は50ユーザーまで無料なので、管理者2人（`profiles.sql:46` の2メール）を Google 認証で絞れば、本番の管理画面 → `wss://` → Tunnel → ローカルの中継サーバ（kotoba-tensei の Origin 張り替えと同じ）→ codex app-server が組める。アプリを Cloudflare へ移す前でも使える（Tunnel はホスティングと独立。Cloudflare 管理下のドメインが1つ要る）。制約は「管理者のPCが起きているときしか動かない」だが、管理者＝利用者2人なので実態と合う。夜間に勝手に動かないことは課金・暴走の面ではむしろ利点。

**位置づけ**: 本書の決定的レンダリング（§0.2〜）をそのまま出荷する（これ自体が $0）。生成が本当に必要になったとき（管理画面からの指示出し等）の拡張経路として、まず無料の Tunnel 案、規模が出たら Containers 案を採る。いま作らない。

### 0.2 生成そのものをやめた理由

外部AIを呼ばない代わりに「Claude Code がオフラインで分析JSONを書き、検査して取り込む」形を設計した。しかし**その設計自身の制約が、生成の必要性を消していた。**

前段のレビューで、性格タイプによるラベリングの害を潰すために次の制約をかけた。

- 僅差軸（3-2）を根拠にできない
- 根拠は同一軸の設問2件以上（1問だけの二択に断定の許可証を与えない）
- 一方に偏りすぎた設問は根拠にできない（測っているのは教室の規範であって個人差ではない）
- 発言や出番を減らす方向の提案を書けない
- 要約1文を書かない（要約はラベルになる）
- 係の推薦を書かない

この全部をかけると、**書ける行動は「どの極が決定的か × どの方向に足すか」の組み合わせに収束する**。18人のクラスで I が決定的な生徒が6人いれば、同じ文面のカードが6枚並ぶ。生成物は入力から決定的に計算できる大きさしか残らない。

数字でも確認した。各軸5問の二択なので、1軸が3-2になる確率は 20/32 = 62.5%。全4軸が3-2（＝「言えることなし」）になるのは、回答が完全にランダムなら15.3%、**軸内に一貫性があれば1〜5%**（18人なら0〜1人）。つまり「制約が厳しすぎて何も出ない」のではなく、**ほとんどの生徒に対して、決まりきった文が出る**。

### 0.3 決定的レンダリングにすると何が消えるか

生成をやめると、前段の設計にあった次のものが**全部不要になる**。

| 消えるもの | なぜ要らなくなるか |
|---|---|
| 書き出し・取り込みスクリプト | 生徒データをファイルに出さない |
| `ai_analyses` テーブルと RLS | 保存するものが無い |
| 30日の実削除 | 保存しないので失効も要らない |
| 入力ハッシュ・鮮度バッジ | 常に最新のスコアから組み立てる |
| 取り込み時の10個の機械検査 | **CIで走る単体テストになる**（実行時に検査するより強い） |
| service_role をスクリプトから使う口 | スクリプトが無い |
| `tmp/` に置く生徒データの平文ファイル | 作らない |
| 誰がいつ回すかという運用の穴 | 回す作業が無い |

**そして生徒データがこの機能のために外へ出ることが一度も無くなる。**

### 0.4 「外部に送らない」の正確な意味

前段の設計では「アプリが外部AIを呼ばない」ことを「生徒の回答が外部に出ない」と読める書き方をしていた。**これは誤りだった。** Claude Code が入力ファイルを読むことは、Anthropic に送ることである。送信先が Google から Anthropic に変わっただけで、外部サービスへ出る事実は変わらない。

本設計ではその問題自体が消える。**台帳は「どの極の生徒に、どの方向の一手を出すか」を書いたものであり、生徒の回答から作らない。** 材料は20問の設問文（既にリポジトリにある公開コンテンツ）と 07 の16タイプ台帳だけ。だから台帳を Claude Code に書かせても、生徒データは1バイトも動かない。

### 0.5 最上位の制約 — 生徒に見せられないことは書かない

**台帳に書いてよいのは「生徒本人が読んでも、07の結果画面と矛盾しない文章」だけとする。** 配布はしない。しかし内容は配布可能でなければならない。

漏洩経路は現実に3つある（教室でのダッシュボード投影・教員PCの画面・スクリーンショット）。07の結果画面で「あなたは **ささえ役**。こまって いる 人に 気が ついて、手を かす」と前向きな自己像を受け取った学生が、教師の画面で同じ20問から作られた別の文章を見たとき、彼が受け取るのは「自分は本当はこう思われていた」ではなく **「あの結果画面は自分に見せるための嘘だった」** である。01ガイドが積み上げた心理的安全（P8・失敗カタログ12）が、**二枚舌の発覚によって遡って無効化される**。

秘密であること自体が損害を増幅する。だから「見せない」ではなく「見せられる内容しか書かない」を制約にする。

**この制約は決定的レンダリングでは構造的に守れる。** 台帳は有限（§2）で、一度だけ §11 のチェックを通せばよい。生成のたびに自己採点する必要が無い。

## 1. 全体の形

```
一度だけ（開発時・人の検収つき）
  Claude Code が 20問の設問文と 07 の16タイプ台帳を読み、
  「極 × 方向」の定型文台帳を書く（行動＋合っていないサイン）
        ↓
  src/content/teaching-hints.ts        ← 生徒データを含まない。PUBLICリポジトリに置ける
  §11 の文言チェック＋ npm run lint:content ＋ 単体テストを通す
        ↓
毎回（実行時・アプリの中だけ）
  管理画面が scores とクラス集計から決定的に組み立てて表示する
  保存しない・生成しない・外に何も出さない
```

台帳を書き足す・言い回しを直すのは、**コンテンツの変更**として通常のレビューとコミットで行う。`PERSONALITY_TYPES` の16タイプ×4行を書いたときと同じ扱いにする。

## 2. 定型文台帳 `src/content/teaching-hints.ts`

### 2.1 何を持つか

```ts
/**
 * 教師の行動の向き。**減らす方向（reduce-*）は定義しない。**
 * 「指名を控える」「後回しにする」はこの学習者集団に対して構造的に有害（§5）。
 */
type HintDirection = "add-choice" | "add-turn" | "add-scaffold";

interface TeachingHint {
  readonly axis: PersonalityAxis;
  /** どちらの極が決定的なときに出すか。 */
  readonly pole: PersonalityPole;
  readonly direction: HintDirection;
  /** 教師の行動。動詞で終える。生徒が読んでも成り立つ文にする（§0.5）。 */
  readonly action: string;
  /** **その行動をしている最中に**観測できる、合っていないサイン（§2.3）。 */
  readonly counterSign: string;
}
```

8極（E/I・S/N・T/F・J/P）× 各1〜2件で、**全体で10〜16件**の有限の台帳になる。

### 2.2 個別に出せるのは `add-choice` と `add-turn` だけ

01ガイド P11 は「負荷の調整装置を学習者自身が握る」であり、アンチパターンは「低い方に割り当てられた学習者のモチベーションが下がる」こと。ふりがなトグルや Drag/Type トグルを本人が選ぶ設計にしておきながら、足場だけ教師が生徒ごとに事前に決めるのは筋が通らない。

- **`add-choice`** — 選べるようにする（「見本を見る／見ないで やってみる を本人に選ばせる」）
- **`add-turn`** — 出番を作る（「ペアで先に言う時間をとってから、全体で聞く」）
- **`add-scaffold`** — 足場を足す（「提出物に中間チェックの日を1つ入れる」）。**クラス全体に等しく与えるものにしか使えない。個別カードには出さない**

型で分けず運用で守ると必ず崩れるので、**個別の選択関数は `add-scaffold` を除外して返す**（§3.2）。テストで固定する。

### 2.3 `counterSign` は行動と対にする

「外れているサイン」をカード全体に1つ付ける形だと自己封止する。

> 悪い例: 行動「発問のあと30秒書く時間を置いてから指名する」／サイン「自分から口火を切ることが多い」

この行動を実行した教室では、**「自分から口火を切る」場面そのものが発生しなくなる**。反証条件が介入によって観測不能になり、予言の自己成就の閉ループになる（教師の期待 → 扱いの変更 → 反証機会の消滅 → 期待の確証）。

> 良い例: 行動「発問のあと30秒書く時間を置いてから指名する」／サイン「**30秒たっても書き出せていない**」

**サインは、その行動を実行している最中に観測できるものでなければならない。** 台帳で行動と対にすることで、この条件を構造的に強制する。

### 2.4 性別・国籍・年齢の軸を持たない

台帳のキーは `axis` と `pole` だけである。**属性ごとの一般化を書く場所が存在しない。** 禁止語で止めるのではなく、データ構造で不可能にする。

ダッシュボードが「16タイプ×性別のクロスは1人だけのセルが並んで個人が特定できてしまう」として家族単位に丸めている（`src/app/admin/page.tsx:221-224`）のと同じ規律。

## 3. 個別カードの組み立て（決定的）

`src/lib/teaching-hints.ts` の純関数。Supabase を import しない（`personality-stats.ts:86-89` が `PERSONALITY_VERSION` を引数で受けている理由と同じ。純関数のテストにSupabaseを混入させない）。

### 3.1 決定的軸を決める

```
① scores から 5-0 / 4-1 の軸を拾う（3-2 は僅差なので除外）
② そのうち、偏り設問を除いても決定的なままの軸だけを残す（§3.3）
③ 残った軸ごとに、その極の hint を台帳から引く
④ add-scaffold は個別では出さない（§2.2）
```

**僅差の判定は1か所に持つ。** 既存の `getCloseAxis`（`src/content/personality.ts:1121-1124`）は **EI→SN→TF→JP の順で最初の1軸しか返さない**。結果画面が「どちらも あなたの いい ところ」を1行だけ出す用途にはそれでよいが、ここでは使えない（`{ei:3, sn:4, tf:2, jp:5}` の生徒で `tf` が漏れる）。定義が2か所に散ると片方だけ直されて壊れるので、述語を切り出して `getCloseAxis` もその上に載せ替える。

```ts
/** その軸が 3-2 の僅差か。「僅差」の定義はここ1か所に持つ。 */
export function isCloseAxis(scores: PersonalityScores, axis: PersonalityAxis): boolean {
  assertScores(scores);
  return scores[axis] === 3 || scores[axis] === 2;
}

/** 僅差の軸すべて。 */
export function getCloseAxes(scores: PersonalityScores): readonly PersonalityAxis[] {
  assertScores(scores);
  return PERSONALITY_AXES.filter((axis) => isCloseAxis(scores, axis));
}

/** 既存の1件版はこの上に載せ替える（07 §4.3 の表示は最初の1つだけ使う）。 */
export function getCloseAxis(scores: PersonalityScores): PersonalityAxis | null {
  return getCloseAxes(scores)[0] ?? null;
}
```

`tests/personality.test.ts:273` の「`{ei:5, sn:4, tf:3, jp:2}` → `"tf"`」は載せ替え後も通る（順序が保たれるため）。

### 3.2 出力

```ts
interface StudentHints {
  /** 0〜3件。**0件は正規の出力**（§3.4）。 */
  readonly hints: readonly TeachingHint[];
  /** 僅差の軸を「教室で確かめること」に変換したもの。 */
  readonly closeAxes: readonly PersonalityAxis[];
  /** 偏り設問のせいで決定的から外した軸（§3.3）。画面に理由を出す。 */
  readonly droppedBySkew: readonly PersonalityAxis[];
}
```

**要約の1文を持たない。** 要約を出すと、教師の記憶に残るのはその1文だけになり、それがラベルになる。18人ぶん並べれば18行のラベル台帳ができ、職員室で口頭で流通する。**カードは行動から始める。**

### 3.3 偏った設問は軸スコアからも外して判定し直す

一方が極端に偏った設問は、**個人を区別する力がほぼ無い**。測っているのは教室の規範であって個人の性質ではない。ましてカンボジアの教室で「先生の前ですぐ手を挙げる」ことの意味が、設問を作ったときに想定した意味と同じである保証は無い。

問題は、偏り設問が**軸スコアにも算入されている**ことである。Q13 が18人中15人 I に偏れば全員の `ei` が I 側に+1され、実質3-1の軸が4-1として「決定的」扱いになる。したがって:

> **偏り設問を除いた残りの設問だけで数え直しても決定的（反対側が1以下）である軸だけを使う。**

`droppedBySkew` に落ちた軸は画面に「この軸は、クラスのほぼ全員が同じ選択をした設問に支えられています。個人の差としては読まないでください。」と出す。

**偏りの閾値と n 下限**:

- 一方が **80%以上** を偏りとする
- ただし **回答者8人未満のコホートでは偏り判定をしない**。n=5 で五分五分の設問が「一方80%以上」になる確率は 12/32 = 37.5%、n=3 なら 25% あり、**小規模では設問の1/4〜1/3が雑音で「使えない」に落ちて材料が消える**。n<8 のときは偏り判定を行わず、代わりに画面に「回答者が少ないため、設問の偏りは判定していません」と出す
- 判定には `calculateQuestionStats`（`src/lib/personality-stats.ts:264`）を再利用する。`percentage` は回答者2人以下で null になるので、`count / total` から自前で比を出す

### 3.4 「言えることがない」を正規の出力にする

4軸すべてが3-2の生徒には `hints: []` を返す。3枠のテンプレートを与えれば3枠は埋まってしまうので、**最も情報が少ない生徒に対して最も根拠の薄い断定が出る**という最悪の形を、型と関数で防ぐ。

画面には「この20問からは、明日の授業を変える根拠は出せませんでした。目の前の様子で判断してください。」だけを出す。

**テストで固定する**: 全軸3-2のスコアで `hints` が0件になること。

### 3.5 手動でタイプを変えた生徒にはカードを出さない

教師が手でタイプを変えたということは、**教師が「回答の結果は目の前の生徒と合わない」と判断した**ということである。そこに回答に基づく行動指示を出すのは、教師が既に否定したデータで押し返す動作になる。

`pickPersonalityCode(scores) !== personality_type` の行（`src/app/admin/users/page.tsx:196-198` が既に「手動変更あり」バッジで可視化している）では、カードの代わりに「タイプを手で変更しています。回答に基づく表示はしません。」と出す。

### 3.6 教師が伏せられるようにする

反証サインを見て「これは合っていない」と判断した教師が、そのカードを消す経路が要る。無ければ、外れたメモが学年末まで画面に出続ける。

`profiles` に `hints_muted boolean not null default false` を足し、個別レポートのカードに「このヒントは合いませんでした」ボタンを置く。押すと以後そのカードを出さない。**押した理由は保存しない**（理由の蓄積は新しいラベルになる）。

## 4. クラスカードの組み立て（決定的）

### 4.1 出すもの

| # | 内容 | 元データ |
|---|---|---|
| 1 | **割れている設問**（40〜60%）と、そこから引く一手 | `calculateQuestionStats` |
| 2 | **偏っている設問**（80%以上）の注記。「設問が一方向に働いている可能性があります」 | 同上 |
| 3 | **回答言語の内訳**と、途中で切り替えた人数（§5） | `answer_language` / `language_switched` |
| 4 | **前回から軸が動いた人数**（§4.3） | `personality_results` の履歴 |

**チームに一切言及しない。** ダッシュボードではカードとチーム名簿が同じ画面に並ぶ。「チーム2は『けいかく』の学生がいません」という文と、チーム2の名簿（実名）が同時に投影された瞬間、4人の名前と「足りない役割」が公開で結びつく。文言で禁じたものをレイアウトで実現しない。**カードはチーム編成セクションより下に置く**（§7.2）。

### 4.2 割れている設問こそ材料になる

18人中10人／8人に割れた設問（例: Q8 の締め切りへの向き方）は、ペアの組み方・課題の出し方という教師の実際の決定に直結する。**偏りの強い設問より、割れている設問のほうが情報量が多い。** クラスカードの主産物はここに置く。

### 4.3 受験履歴の差分を主産物のひとつにする

`personality_results` は追記専用の台帳で、2回目以降の受験が残る。**「4月は E4 だった生徒が、7月は E2 になっている」は、この設計が最も恐れる「性格は固定のラベル」への直接の反証である。**

- クラス: 「前回から軸が動いた人が◯人います。」— 性格が固定ラベルでないことの実証
- 個別: 「前回（◯月◯日）と答えが変わった設問は Q5・Q12 です。その日の気分や、そのあとの経験の変化かもしれません。」

**版が違えば比較しない**（既存の `calculateResultChange` が `{comparable:false, reason:"version-mismatch"}` を返す規律をそのまま使う）。**「性格が変わった」とは書かない。** 変わったのは回答である。

履歴は**直近3件まで**に切る。全件を無制限に読むと、受験を重ねた生徒だけカードが長くなる。

## 5. 回答言語の交絡 — この設計で最も重い問題

### 5.1 何が起きるか

この20問は N5〜N3 のカンボジア人学生が**第二・第三言語で**答える。`src/components/welcome-wizard.tsx:286` の言語トグル（やさしい日本語／日本語／English）は `useState<PersonalityLanguage>("easy")` のローカル状態で、**どの言語で答えたかがどこにも保存されていない**。クメール語版は無く、設問の途中で切り替えることもできる。

つまり、回答が本人の傾向を表しているのか、**設問の日本語が読めた／読めなかったか**を表しているのかを、教師も画面も原理的に区別できない。

> 日本語が一番苦手な学生がいる。Q13の2択で、短くて意味の取りやすいほうを選ぶ。実際に彼が手を挙げないのは内向性ではなく、01ガイド §1.1 の「間違えたら恥ずかしいという不安」である。画面は I 側のヒントを出す。教師は彼を指名するのをやめる。**日本語が最も苦手な学生が、日本語を話す機会を最初に失う。** 半年後、彼は診断どおり「考えてから話す学生」になっている。

これは 01ガイド §4 失敗カタログ1「**言語が苦手＝能力が低い、という描き方は禁止**」（キャラ田中優太を全廃した規律）の、教師の行動レベルでの再現である。同時に P6（産出機会を削らない）にも正面から反する。

`personality.ts` のコメントは、作者自身が言語起因の偏りを既に3問で潰した記録を残している（Q8「いきおいを つけて やる」はN1慣用句／Q19「やさしいね」の誤読／Q14 のかんじ誤読）。**潰しきれていない残余があるという前提で設計する。**

### 5.2 対策（3つとも必須）

1. **回答言語を記録する。** `personality_results` と `profiles` に `answer_language` と `language_switched` を足し、ウィザードが保存する（§8）。
2. **注記は全員に出す。** 条件を付けない。
   > この回答は、やさしい日本語・日本語・英語のいずれか（本人にとって第2・第3の言語）で行われています。発言が少ないことは、日本語への不安によることがあります。

   **`easy`（やさしい日本語）を除外しない。** easy は既定値であり、既定のまま進む生徒は日本語がいちばん不安な層とちょうど重なる。**注記を一番届けたい相手にだけ出ない、という条件を書かない。**
3. **発言や出番を減らす方向を型で存在させない。** `HintDirection` に `reduce-*` を定義しない（§2）。「指名を控える」「後回しにする」「待つ時間を長くする」は、この学習者集団に対しては構造的に有害。許すのは足す方向だけ。

### 5.3 係の推薦は出さない

`teamRole`（「きろく役」「ささえ役」…）は 07 の**学習者向け結果画面で本人に前向きな自己像を渡すためのラベル**である。教師が実在の係を割り当てる規則に転用すると機能が反転する。

> ISFJ と判定された学生が、M1 から M12 まで、担当教師が代わっても毎回「議事録係が合いそうです」と提案され、毎回議事録を書く。**発表係は一度も回ってこない。** このプログラムの裏の目的（01 §1.2 = 日本語で聞く・話す・書く）のうち「話す」の機会が、20問のアンケートによって12モジュールぶん配分から外れる。

係の配分は「全員に一巡させる」がこのプログラムの既存原則（waterfall_quest の P1 実装例）である。**台帳に `teamRole` を参照する項目を持たない。**

## 6. 検査

生成が無いので、検査は**台帳の検収（一度きり・人の目）**と**選択ロジックのテスト（CIで毎回）**の2層になる。

### 6.1 台帳の検収（`src/content/teaching-hints.ts` を書いたとき）

§11 のチェックリストを人が通す。加えて `npm run lint:content` が自動で走る。

**禁止語は既存の定数を再利用する。** `scripts/lint_content.ts:205` は `walkSource(SRC_DIR)` で `src/` 全体の文字列リテラルを走査し、免除されるのは変数名が `FORBIDDEN_LEARNER_WORDS` の宣言配下だけ（同 :95-105）。**別名の定数に「不正解」「間違い」「ダメ」を書くと `npm run lint:content` が必ず落ちる。** 追加の禁止語を持つときは `FORBIDDEN_LEARNER_WORDS`（`src/content/schema.ts:13-19`）を import して合成する。

追加で見る語（教師向け文にだけ効く。学習者向けの禁止語とは別リスト）:

| 分類 | 落とす語 |
|---|---|
| 能力・将来の予測 | 向いていない / 素質 / 伸びにくい / 適性 |
| 欠損表現 | 弱い / 苦手 / できない / 劣る / 足りない |
| 人格の固定 | 〜な性格です / 〜な人間です |
| 比較・序列 | いちばん〜 / 〜より |
| 相性の否定 | 合わない / 離したほうが |
| 測っていないもの | ストレス / メンタル / 家庭 / 発達 |
| 警戒 | 要注意 / 気になる |

**禁止語リストでは欠損フレームは止まらない。** 「即指名は沈黙になりやすい」「見本がないと入れない」はどれも禁止語を含まないのに実質は欠損の言い換えである。だから本体は §6.2 の構造テストと §11 の目視に置く。語彙検査は補助でしかない。

## 8. DBの変更（これだけ）

```sql
alter table public.personality_results
  add column if not exists answer_language text
    check (answer_language is null or answer_language in ('easy', 'japanese', 'english'));
alter table public.personality_results
  add column if not exists language_switched boolean not null default false;

alter table public.profiles
  add column if not exists answer_language text
    check (answer_language is null or answer_language in ('easy', 'japanese', 'english'));
alter table public.profiles
  add column if not exists language_switched boolean not null default false;

alter table public.profiles
  add column if not exists hints_muted boolean not null default false;
```

- **`answer_language` は not null にしない。** `null` は「記録前のデータ」を意味する。既存行を偽の値で埋めない
- `check` を `is null or ...` にするのは、NULL が CHECK を通ることに依存せず意図を明示するため
- **既存の CHECK と衝突しない**ことを確認する。`20260727120000_personality_v3.sql` の制約は `answers` と `scores` の対だけを見ており、列の追加では発火しない
- `if not exists` で冪等にする（既存マイグレーションの作法に合わせる）

ウィザードは診断完了時に、そのとき選ばれていた言語と、途中で切り替えたかどうかを保存する。**保存に失敗しても学習を止めない**（記録台帳の insert 失敗を握りつぶしている `welcome-wizard.tsx:381-389` と同じ構え）。

## 9. やらないこと

1. **成績・進級・就職適性の予測** — 学習データが存在しない。性格→学力の推論に根拠が無く、生徒の進路に実害が出る
2. **「要注意生徒」の自動抽出・アラート** — 性格の回答から警戒対象は定義できない
3. **自由質問チャット** — 引用規律も禁止語検査も守れず、データ外（家庭・メンタル・能力）への推測に必ず滑る
4. **相性ワースト・「離すべきペア」** — 07 §5 が学習者向けに封じた枠組みを、教師向けの裏口から復活させることになる。席替えという行動を通じて生徒に伝わる
5. **要約1文** — 要約はラベルになる（§3.2）
6. **係の推薦** — §5.3
7. **分析文のDB保存** — 保存しない。これが §0.3 の消去リストの中心
8. **定期自動実行・「性格が変わった」監視** — 性格は監視すべきメトリクスではない。履歴の差分は「答えが変わった設問」の列挙まで（§4.3）
9. **性別・国籍・年齢による一般化** — 台帳にその軸を持たない（§2.4）
